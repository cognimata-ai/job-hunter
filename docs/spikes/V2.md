# V2: stalled procrastinate jobs after a worker dies

## Assumption

procrastinate 3.10.0 detects the jobs of a worker that is gone and can release them, so that a job the killed
worker held in `doing` runs again (spec §3.3.2, §17.4 `stalled_jobs`, §22 V2).

## Method

Crash test `tests/crash/test_v2_stalled.py::test_v2_killed_worker_job_is_released`, against the digest-pinned
PostgreSQL container:

1. `tests/crash/stall_worker.py` starts a procrastinate worker (queue `aux`, heartbeat every second), defers one
   job and runs it. The job prints `stall_job_started` from inside and then sleeps.
2. The test waits for that event, sends `SIGKILL`, and checks the exit status.
3. It ages `procrastinate_workers.last_heartbeat` by 5 minutes (the test never waits for the 60 s to pass), calls
   `release_stalled_jobs`, and reads the job's status.

Integration tests in `tests/integration/test_queue.py` cover the two ways a single release can go wrong, with jobs
set to `doing` without a worker: `test_stalled_job_with_a_taken_queueing_lock_is_failed_and_the_rest_are_released`
and `test_job_that_finished_after_the_listing_is_skipped` (the job is moved to `succeeded` between the listing
and the retry).

## Observed result

The names of 3.10.0 are as the plan assumed. The retry call differs from what the plan took for granted.

- `JobManager.get_stalled_jobs(seconds_since_heartbeat=...)` returns the jobs in `doing` whose worker has no
  heartbeat for longer than that, and those whose `worker_id` is NULL. The latter matters: a live worker prunes
  workers that missed their heartbeat for `stalled_worker_timeout` (30 s by default) and the foreign key sets
  `procrastinate_jobs.worker_id` to NULL, so the job is found whether or not the worker row still exists.
- `JobManager.retry_job(job)` calls the SQL function `procrastinate_retry_job_v2`. It accepts a job in `doing`
  **or `failed`** and moves it to `todo` (counting the attempt; a `doing` job with an abort request becomes
  `failed` instead). For a job in any other status, or no job, it **raises** (`RAISE`, "Job was not found or has
  an invalid status to retry"), which the connector surfaces as `procrastinate.exceptions.ConnectorException`.
  So a second release of the same job is an error, not a no-op.
- The retry can also fail on the unique index `procrastinate_jobs_queueing_lock_idx_v1` (one `todo` job per
  queueing lock): when a waiting job holds the stalled job's queueing lock (a dead worker's `tick` while the next
  `tick` already waits), the connector raises `procrastinate.exceptions.UniqueViolation` with
  `constraint_name == procrastinate.manager.QUEUEING_LOCK_CONSTRAINT`.
- `JobManager.finish_job(job, Status.FAILED, delete_job=False)` (`procrastinate_finish_job_v1`) moves a `todo` or
  `doing` job to `failed`; `JobManager.get_job_status_async(job_id)` reads a job's status (`NoResult` for a job
  that is gone).
- After `SIGKILL` the job stayed in `doing` with its worker row. `release_stalled_jobs(app)` (with the default
  `seconds_since_heartbeat=60`) found exactly one job and left it in `todo`.
- `JobManager.delete_old_jobs(nb_hours, include_failed, include_cancelled, include_aborted)` is the retention
  call (`test_delete_finished_jobs_keeps_recent` in `tests/integration/test_queue.py`).

## Decision

`jobhunter.worker.tasks.release_stalled_jobs(app, *, seconds_since_heartbeat=60.0)` lists the stalled jobs with
`get_stalled_jobs` and handles each one on its own, so that one job cannot keep the others from being released.
Every M0 task is idempotent, so a stalled job is retried, not failed:

- `retry_job` succeeds: the job is released and counted (log `stalled_job_released`).
- The retry hits the queueing-lock index: the waiting job supersedes the stalled one, which is marked failed with
  `finish_job` (log `stalled_job_superseded`; not counted). Test:
  `test_stalled_job_with_a_taken_queueing_lock_is_failed_and_the_rest_are_released`, in both listing orders.
- The retry raises `ConnectorException` and the job is no longer in `doing` or `failed` (it ended after it was
  listed, or was released meanwhile): the job is skipped (log `stalled_job_not_retryable`; not counted). Test:
  `test_job_that_finished_after_the_listing_is_skipped`. The status is read back to tell this from a database
  failure, so the message of the SQL `RAISE` is not parsed.
- Any other error propagates, and the `stalled_jobs` reconciler records it as `reconciler.failed`.

A job that fails late (after being listed as stalled, with status `failed`) is accepted by
`procrastinate_retry_job_v2` and so is retried once more; this is harmless because every M0 task is idempotent.

`release_stalled_jobs` is called by the `stalled_jobs` reconciler (`jobhunter.worker.reconcilers`, cadences
`start` and `tick`) and by nothing else, so it is the one release path.

The run that the job belongs to resumes as a new attempt through the `stale_runs` reconciler and the takeover
sweep, not here. Task 13 sets the worker's heartbeat interval; the 60 s threshold then covers several missed
heartbeats (the procrastinate default interval is 10 s).
