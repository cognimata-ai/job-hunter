# V7: the arctic-embed-l-v2.0 ONNX export, its throughput, memory and parity

This record is the container part (Task 21): this development container, with its CPU. The run of spec §22 V7
on the provisioned VPS is repeated at deployment (§23: the VPS is chosen then), with the same script.

**Outcome.** The int8 export missed the parity criterion (min 0.9720 against fp32, below 0.99). Following the
rule of the plan, `embedder/model.lock` now pins `onnx/model_fp16.onnx` of the same revision, with `model_id`
`snowflake-arctic-embed-l-v2.0@ac6544c8a46e00af67e330e85a9028c66b8cfd9a/fp16`. On this CPU the fp16 export
meets the parity and the query-prefix check, but misses both the throughput criterion (0.51 docs/s at 1,024
tokens) and, narrowly, the memory criterion (3.18 GB peak RSS). It is also slower and larger here than the
fp32 export. The deployment run decides; the options are listed at the end.

## Assumption

§22 V7: the int8 ONNX export of `Snowflake/snowflake-arctic-embed-l-v2.0` embeds at ≥ 1.5 docs/s at 1,024
tokens with RSS ≤ 3 GB, its cosine parity with the fp32 export is ≥ 0.99 on 50 ads, and query-prefix handling is
verified. Otherwise the fp16 export is used (§19.7).

## Method

- **Model files.** Revision `ac6544c8a46e00af67e330e85a9028c66b8cfd9a`, downloaded with
  `embedder/download_model.sh` (curl from `huggingface.co/<repo>/resolve/<revision>/<file>`, then
  `sha256sum --check` against the lock) into the gitignored `.model-cache/`. Every sha256 matched the values of
  the brief and of the revision's Hugging Face LFS metadata:

  | File | Bytes | sha256 |
  |---|---|---|
  | `onnx/model_int8.onnx` | 569,721,975 | `4b164a8bd09dd9806e035bdf3c34a2d81848b3db9642ba2e342b8367c00872d8` |
  | `onnx/model_fp16.onnx` | 1,134,153,607 | `0b6846bcf4c0d9e53fdfc70d6dc1bbe3bb40fd205ebb7f0365da5b07064ddccc` |
  | `onnx/model.onnx` (fp32) | 702,280 | `f74aa79745ccfb1e75daa7e8e6552a78402d4de193eb8ca67a931358d3e0a25e` |
  | `onnx/model.onnx_data` (fp32) | 2,266,886,160 | `fe7d75ff258fbda10a6bea63c5422df5579d625355b1aca69ba6923c0ba604a9` |
  | `tokenizer.json` | 17,083,074 | `39feb9863a378165ab9c5c689047203d789422966c0c58721c5309fd039a8edc` |

  The fp32 reference was downloaded only for this spike, with the same script and a scratch lock of its three
  lines (`MODEL_LOCK=.model-cache/fp32.lock embedder/download_model.sh .model-cache/arctic-fp32`), and was
  deleted after the runs.
- **Code.** `scripts/spikes/v7_embedder.py` loads the service's own `embedder.app.OnnxModel`: the export's
  tokenizer truncating at 1,024 tokens, one inference per text, the `sentence_embedding` output, L2-normalised
  float32. It checks `model.lock` and the sha256 of every file it uses before measuring.
- **Corpus.** The descriptions of 50 ads of the committed scrubbed fixtures (never `.fixtures-raw/`):
  `arbeitnow/page1.json` (30), `jsearch/search_v2_page1.json` (10) and `serpapi/google_jobs_hl_en.json` (10),
  each as the adapter stores it in `description_text`. Untruncated, they are 287 to 2,252 tokens long
  (median 1,080); 27 of the 50 exceed 1,024 and are truncated.
- **Throughput.** After one warm-up text, the 50 ads are embedded as passages in requests of 16, as the embed
  node sends them (§9.2): **A** the ads as stored (mean 901 tokens after truncation), and **B** each ad
  repeated until it is over 1,024 tokens, so that every text is exactly 1,024 tokens. B is the criterion's
  figure. All runs use 3 intra-op threads (`EMBEDDER_THREADS`'s default, the service's `cpus: 3`) and 1
  inter-op thread.
- **Memory.** The process's peak RSS (`resource.getrusage`, `ru_maxrss`), read after A and B and before the
  fp32 reference is loaded. GB means 10⁹ bytes; MiB is given too.
- **Parity.** The same 50 texts through the fp32 export with the same code; the cosine of each ad's two
  vectors. The criterion is applied to the minimum over the 50 ads.
- **Query prefix.** `python developer` embedded as a query (`query: ` prefixed) against two short ads written
  for the spike, a Python developer ad and an intensive-care nurse ad (the fixtures hold no nursing ad), and
  against the same text embedded as a passage. On the fixtures as well: the query against the 12 ads that
  mention Python and the 38 that do not.
- **Machine.** Intel Xeon (virtualised), 4 CPUs (1 thread per core), AVX-512 VNNI, 15 GiB; onnxruntime 1.31.0,
  tokenizers 0.23.3, numpy 2.5.4. No other test run was seen before or during the runs (`pgrep`, `ps`). The
  1-minute load average at the start was 0.13 (first int8 run) and 0.23 (fp16); the later runs of the same
  sequence started at 2.6 to 2.9, which is the decay of the run just before them, and the int8 rerun
  reproduced the first int8 run within 2 %.

Commands (run from the repository root):

```bash
embedder/download_model.sh .model-cache/arctic
uv run --group embedder python scripts/spikes/v7_embedder.py .model-cache/arctic \
    --fp32 .model-cache/arctic-fp32 [--onnx onnx/model_int8.onnx]
uv run --group embedder python scripts/spikes/v7_embedder.py .model-cache/arctic --padded-batch 16 \
    --fp32 .model-cache/arctic-fp32 [--onnx onnx/model_int8.onnx]
```

3.24 GiB of the 3.42 GiB limit.

## Decision

The int8 parity is below 0.99, so the lock moved to the fp16 export with the brief's sha256, as the plan
prescribes for that case. Its `model_id` suffix is `/fp16`: `embeddings.embedding_model_id` keys vectors by
model, and vectors of different exports are never compared (§19.6). The thresholds were not changed, and the
misses above stay misses.

## Other findings

1. **The export pools the CLS token.** Both the int8 and the fp16 export have the outputs `token_embeddings`
   and `sentence_embedding`; `sentence_embedding` is the L2-normalised CLS token (cosine 1.0 with the
   normalised first token on two probes), as the model's `1_Pooling/config.json` prescribes
   (`pooling_mode_cls_token: true`). Mean pooling over the token output gave cosines of 0.84 and 0.87 with it,
   so `OnnxModel`'s fallback for an export without a pooled output is the CLS token, not a mean.
2. **The tokenizer's own settings.** `tokenizer.json` truncates at 512 tokens and pads batches; `OnnxModel`
   sets the truncation to 1,024 and turns padding off.
3. **One text per run, not padded batches.** `--padded-batch 16` ran the 1,024-token ads as padded batches of 16
   directly through onnxruntime. It was slower (int8 1.23, fp16 0.46 docs/s), its peak RSS was far higher
   (int8 5.41 GB, fp16 6.83 GB: over the 3.5 GB limit), and with int8 the shortest ad's vector, padded next to a
   1,024-token ad, moved to cosine 0.974262 with its vector alone (fp16 and fp32: 1.000000). The int8 export
   quantises activations with one scale per tensor, padding included. `OnnxModel` therefore runs each text on
   its own; alone or next to a 1,024-token text, a vector is the same (cosine 1.000000, both exports).
4. **fp16 is slower and larger than fp32 on this CPU.** Without native fp16 arithmetic the fp16 export runs
   below the fp32 one (0.51 against 0.53 docs/s at 1,024 tokens, 0.58 against 0.62 to 0.64 on the stored ads)
   and needs more memory (3.18 against 2.05 GB). §19.7's remedy for a slow int8 ("the fp16 export is used
   instead") would make throughput worse on a CPU like this one: int8 is 2.7 to 2.9 times faster.
5. **onnxruntime telemetry.** onnxruntime 1.31.0 on Linux embeds Microsoft's 1DS telemetry: it writes a device
   id and an event store under `~/.cache/Microsoft/DeveloperTools/.onnxruntime` and posts to
   `mobile.events.data.microsoft.com`. Only `ORT_DISABLE_TELEMETRY=1`, set before onnxruntime is imported,
   stopped it (`disable_telemetry_events()` after the import did not). The image sets the variable, and
   `OnnxModel` sets it before its import; `tests/embedder` checks that loading the model writes nothing under
   `HOME`. In the stack the embedder has no route to the internet in any case (§16.9).

## Open for the deployment run (§22 V7 on the VPS, §23)

The VPS run repeats both measurements. The options, on this container's figures:

- **fp16, as locked**: exact parity; about 0.5 docs/s at 1,024 tokens, so 1,000 new ads take about 30 min of
  the embedder's 3 CPUs (§19.7 assumed under 10 min); 3.18 GB peak RSS, within about 0.2 GiB of the
  `mem_limit: 3500m` once the page cache is counted.
- **int8**: 1.36 to 1.66 docs/s and 1.68 GB, but a parity of 0.972 to 0.978, below the criterion.
- **fp32** (`onnx/model.onnx` + `onnx/model.onnx_data`): exact; on this CPU slightly faster than fp16 and
  smaller (2.05 GB). It is not a fallback the spec names.
