# V7: the arctic-embed-l-v2.0 ONNX exports: throughput, memory and parity

This record is the container part (Task 21), measured in this development container on its CPU. The §22 V7 run
on the provisioned VPS is repeated at deployment (§23: the VPS is chosen then), with the same script.

**Outcome.** No export meets all three criteria on this CPU. The int8 export misses the parity (min 0.9720
against fp32, below 0.99). The fp16 export, the spec's fallback, is slower and larger than fp32 here. By
controller ruling T21-a, `embedder/model.lock` pins the **fp32** export for M1 (`onnx/model.onnx` with its
external data `onnx/model.onnx_data`). Its `model_id` is
`snowflake-arctic-embed-l-v2.0@ac6544c8a46e00af67e330e85a9028c66b8cfd9a/fp32`. fp32 meets the parity (it is the
reference), the query-prefix check and the memory criterion, and misses the throughput criterion (0.57 docs/s at
1,024 tokens). This is a recorded deviation from §19.7, and the deployment run decides again.

## Assumption

§22 V7: the int8 ONNX export of `Snowflake/snowflake-arctic-embed-l-v2.0` embeds at ≥ 1.5 docs/s at 1,024 tokens
with RSS ≤ 3 GB; its cosine parity with the fp32 export is ≥ 0.99 on 50 ads; and query-prefix handling is
verified. Otherwise the fp16 export is used (§19.7, which expects fp16 at about 3.5 GB RSS).

## Method

- **Model files.** All files come from revision `ac6544c8a46e00af67e330e85a9028c66b8cfd9a`.
  - Downloaded with `embedder/download_model.sh`, which runs curl against
    `huggingface.co/<repo>/resolve/<revision>/<file>` and then `sha256sum --check` against the lock, into
    the gitignored `.model-cache/`.
  - The sha256 values are the revision's Hugging Face LFS object ids
    (`GET https://huggingface.co/api/models/Snowflake/snowflake-arctic-embed-l-v2.0/tree/<revision>/onnx`,
    `lfs.oid`).
  - The API's int8 and fp16 oids equal the brief's hashes, and every download equals its oid.

  | File | Bytes | sha256 (LFS oid) |
  |---|---|---|
  | `onnx/model_int8.onnx` | 569,721,975 | `4b164a8bd09dd9806e035bdf3c34a2d81848b3db9642ba2e342b8367c00872d8` |
  | `onnx/model_fp16.onnx` | 1,134,153,607 | `0b6846bcf4c0d9e53fdfc70d6dc1bbe3bb40fd205ebb7f0365da5b07064ddccc` |
  | `onnx/model.onnx` (fp32) | 702,280 | `f74aa79745ccfb1e75daa7e8e6552a78402d4de193eb8ca67a931358d3e0a25e` |
  | `onnx/model.onnx_data` (fp32) | 2,266,886,160 | `fe7d75ff258fbda10a6bea63c5422df5579d625355b1aca69ba6923c0ba604a9` |
  | `tokenizer.json` | 17,083,074 | `39feb9863a378165ab9c5c689047203d789422966c0c58721c5309fd039a8edc` |

- **Code.** `scripts/spikes/v7_embedder.py` loads the service's own `embedder.app.OnnxModel`:
  - the export's tokenizer, truncating at 1,024 tokens;
  - one inference per text;
  - the `sentence_embedding` output, L2-normalised float32.

  It checks `model.lock` and the sha256 of every file it uses before it measures. `--onnx` picks the export,
  and the default is the locked one.
- **Corpus.** The descriptions of 50 ads of the committed scrubbed fixtures (never `.fixtures-raw/`):
  - `arbeitnow/page1.json` (30), `jsearch/search_v2_page1.json` (10) and `serpapi/google_jobs_hl_en.json` (10);
  - each description as the adapter stores it in `description_text`;
  - untruncated, 287 to 2,252 tokens (median 1,080), with 27 of the 50 over 1,024 and so truncated.
- **Throughput.** After one warm-up text, the 50 ads are embedded as passages in requests of 16, as the embed
  node sends them (§9.2), in two passes:
  - **A**, the ads as stored (mean 901 tokens after truncation);
  - **B**, each ad repeated until it is over 1,024 tokens, so every text is exactly 1,024 tokens. B is the
    criterion's figure.

  All runs use 3 intra-op threads (the default of `EMBEDDER_THREADS`, matching the service's `cpus: 3`) and 1
  inter-op thread.
- **Memory.** The process's peak RSS (`resource.getrusage`, `ru_maxrss`), read after passes A and B and before
  any reference export is loaded. GB means 10⁹ bytes; MiB is given too.
- **Parity.** The same 50 texts go through the fp32 export with the same code, and the cosine of each ad's
  two vectors is taken. The criterion applies to the minimum over the 50 ads.
- **Query prefix.** `python developer` is embedded as a query (with the `query: ` prefix) and compared with:
  - two short ads written for the spike, a Python developer ad and an intensive-care nurse ad (the fixtures
    hold no nursing ad);
  - the same text embedded as a passage;
  - the 12 fixture ads that mention Python, and the 38 that do not.
- **Machine.** Intel Xeon (virtualised), 4 CPUs (1 thread per core), AVX-512 VNNI, 15 GiB; onnxruntime 1.31.0,
  tokenizers 0.23.3, numpy 2.5.4. No other test run was seen before or during the runs (`pgrep`, `ps`).
  - Load average (1 min) at the start of each clean run: 0.13 (first int8 run), 0.23 (fp16), 0.80 (fp32).
  - The int8 rerun and the padded-batch runs started at 2.6 to 2.9. That is the decay of the run just before
    them; the int8 rerun reproduced the first int8 run within 2 %.

Commands (run from the repository root):

```bash
embedder/download_model.sh .model-cache/arctic                     # the locked files (fp32 + tokenizer)
uv run --group embedder python scripts/spikes/v7_embedder.py .model-cache/arctic \
    [--onnx onnx/model_int8.onnx | --onnx onnx/model_fp16.onnx --fp32 .model-cache/arctic]
uv run --group embedder python scripts/spikes/v7_embedder.py .model-cache/arctic --padded-batch 16 \
    [--onnx onnx/model_int8.onnx] [--fp32 <dir with the fp32 export>]
```

For the int8 and fp16 runs, those two files were downloaded beside the locked ones with a scratch lock of their
oids (`MODEL_LOCK=<scratch lock> embedder/download_model.sh .model-cache/arctic`).

## Decision

**Ruling T21-a: fp32 for M1.** The int8 parity is below 0.99, so §19.7 calls for the fp16 export. On this CPU,
without native fp16 arithmetic, fp16 is strictly worse than fp32:
- slower: 0.51 against 0.57 docs/s at 1,024 tokens, and 0.58 against 0.64 as stored;
- larger: 3.18 against 2.60 GB peak RSS, at 3.24 of the container's 3.42 GiB;
- no better in parity: both are exact.

Presumably onnxruntime's CPU provider runs most fp16 nodes through casts to fp32 (its larger RSS fits a
second copy of the weights); that was not traced. The lock therefore pins the fp32 export. `model_id` ends in `/fp32`, because `embeddings.embedding_model_id` keys
vectors by model and vectors of different exports are never compared (§19.6). The thresholds were not
changed. fp32's throughput miss is recorded, and the controller flags this deviation to the user.

Two further deviations from the brief, both backed by the measurements below:

1. **One inference per text, not padding per batch.** The brief pads the texts of a batch to the batch's
   longest. `--padded-batch 16` ran the 1,024-token ads as padded batches of 16 directly through onnxruntime:

   | Padded batches of 16 vs one text per run | int8 | fp16 | fp32 |
   |---|---|---|---|
   | docs/s | 1.23 vs 1.36 | 0.46 vs 0.51 | not run |
   | Peak RSS | 5.41 GB vs 1.68 | 6.83 GB vs 3.18 | not run |
   | Cos of the shortest ad, padded next to a 1,024-token ad, vs alone | 0.974262 | 1.000000 | 1.000000 |

   Padded batches were slower, and their peak RSS was over the 3.5 GB limit for both exports. With int8 the
   vector also moved: the export quantises activations with one scale per tensor, padding included.
   `OnnxModel` therefore runs each text on its own. A vector is then the same alone and next to a 1,024-token
   text (cosine 1.000000 for every export).
2. **CLS pooling, not mean pooling.** The brief says mean pooling over `last_hidden_state` when the export has
   no pooled output. All three exports have the outputs `token_embeddings` and `sentence_embedding`.
   `sentence_embedding` is the L2-normalised CLS token: cosine 1.0 with the normalised first token on two
   probes, as the model's `1_Pooling/config.json` prescribes (`pooling_mode_cls_token: true`). Mean pooling
   over the token output gave cosines of 0.84 and 0.87 with it. `OnnxModel` uses `sentence_embedding`, and
   its fallback for an export without one is the CLS token.

## Other findings

1. **External data.** The fp32 graph keeps its weights in `onnx/model.onnx_data`, which onnxruntime opens from
   the graph's own directory. `download_model.sh` preserves the lock's paths. `locked_onnx_file` refuses a
   lock whose `.onnx_data` is not `<graph>_data` beside the graph. `verify_checksums` checks the data file
   like any other: a missing `model.onnx_data` exits 78 and names it.
2. **The tokenizer's own settings.** `tokenizer.json` truncates at 512 tokens and pads batches. `OnnxModel`
   sets the truncation to 1,024 and turns padding off.
3. **onnxruntime telemetry.** onnxruntime 1.31.0 on Linux embeds Microsoft's 1DS telemetry. It writes a device
   id and an event store under `~/.cache/Microsoft/DeveloperTools/.onnxruntime` and posts to
   `mobile.events.data.microsoft.com`. Only `ORT_DISABLE_TELEMETRY=1`, set before onnxruntime is imported,
   stopped it; `disable_telemetry_events()` after the import did not.
   - The image sets the variable, and `OnnxModel` sets it before its import.
   - `tests/embedder` checks that loading the model writes nothing under `HOME`.
   - In the stack the embedder has no route to the internet anyway (§16.9).
4. **Image size.** With fp32 the image is 4.84 GB on disk (2.2 GB content). With fp16 it was 2.66 GB, and
   with int8 1.48 GB.

## Open for the deployment run (§22 V7 on the VPS, §23)

On the chosen VPS CPU, the run measures all three exports with the commands above: int8 and fp16 with `--onnx`,
and fp32 as locked, with fp32 as the parity reference. It applies the spec's criteria to each, with
`EMBEDDER_THREADS` at the service's CPU count:
- ≥ 1.5 docs/s at exactly 1,024 tokens (pass B);
- peak RSS ≤ 3 GB, and the running container well inside `mem_limit: 3500m`;
- parity with fp32 ≥ 0.99, the minimum over the 50 ads;
- the query-prefix check passes.

The choice, which the user makes and the lock then records with its LFS oids and `model_id` suffix:
- **int8**, only if its parity reaches 0.99 on that CPU. Here it is 0.972, a property of the export's dynamic
  quantisation, so this likely needs the user to waive the parity criterion. It is the only export near the
  throughput criterion.
- **fp32**, the M1 lock: exact, and within the memory criterion. It is the choice wherever fp16 is not
  accelerated.
- **fp16**, only where the CPU computes fp16 natively (for example AVX-512 FP16 or AMX-FP16) and it then beats
  fp32 on docs/s at 1,024 tokens while staying within RSS ≤ 3 GB.

If no export reaches 1.5 docs/s, the miss is recorded with its daily cost. At this container's figures,
1,000 new ads a day take about 30 min of the embedder's 3 CPUs with fp32 (§19.7 assumed under 10 min with int8).
