# V4: the structured-output schemas on the live API (the schema dry-run)

## Assumption

Spec §22 V4 and §10.11: the conservative JSON-schema subset of the four structured-output schemas is accepted
and not stripped, for every schema × configured model. That subset is `enum`, `anyOf` with null, `$ref`/`$defs`
and nested objects, in the generator (§11.5), critic (§11.7.3), profile (§12.4) and queries (§11.12) schemas.
The acceptance criterion: every case answers 200, its output is valid, and its enums are respected. The
informational `minimum` probe's result is recorded.

## Method

The cases are `llm.schema_dry_run.cases` of the seeded model policy B:
- generator on `claude-sonnet-5-5` (the `generate` and `revise` model);
- critic, profile and queries on `claude-opus-5-5`.

Each case is the exact request the gateway sends for it (`schema_dry_run.prompt_for` and `node_for`):
- the dry-run's static system block (527 bytes);
- one synthetic user turn: a profile and an ad without names or contact data, or a CV for the profile case;
- the mirror's transformed schema (`schemas.transformed`, byte-equal to prompt-schema version 1);
- effort `low`, `max_tokens` 2,000, purpose `schema_dry_run`.

The recorder sent them (`scripts/spikes/record_anthropic.py --spike v4`, definitions in
`scripts/spikes/v4_schema_dry_run.py`), each after a `--dry-run` that built the requests offline and checked the
payloads. The calls ran on 2026-10-21, in two rounds:

1. The first live run sent the generator case. It was answered 400, and the recorder stopped by design ("the
   first unexpected outcome stops the spike"). Nothing else was sent until the controller ruled.
2. Controller ruling R7-2: the remaining gating cases (critic, profile, queries) were sent as 3 paid messages,
   with no retry. The spike module sets `RECORD_EVERY_ANSWER`, so the recorder commits each case's live answer
   as the fake's answer and goes on to the next case.
   - R7-3: `--commit-recorded` then wrote the generator's 400 from its raw capture. It sent nothing.
   - R7-2: the paid probe was **not** sent. The probe went to the free `messages.count_tokens` endpoint
     (`v4_schema_dry_run.py --record-probe-count`).

## Observed result

| Case | Model | Answer | Usage in / out | Checks |
|---|---|---|---|---|
| generator (§11.5) | `claude-sonnet-5-5` | **HTTP 400** `invalid_request_error` | (not billed) | The sent schema is byte-equal to the stored one |
| critic (§11.7.3) | `claude-opus-5-5` | 200 `end_turn` | 1,898 / 326 | All pass |
| profile (§12.4) | `claude-opus-5-5` | 200 `end_turn` | 2,588 / 650 | All pass |
| queries (§11.12) | `claude-opus-5-5` | 200 `end_turn` | 1,058 / 406 | All pass |
| probe: the generator schema with one added `"minimum": 0` (on `$defs.nullable_int`'s integer branch) | `claude-sonnet-5-5`, counting endpoint | **HTTP 400** `invalid_request_error` | (free) | The keyword was on the wire |

"All pass" means: the served model is the requested one, the sent `output_config.format.schema` is byte-equal
(canonical JSON) to the transformed one, the output parsed, and every value is allowed by the schema
(`schema_dry_run.schema_violations`: no violation path, so no enum, `anyOf` or `$ref` was stripped).

**The generator schema is rejected** (R7-1: recorded here, not fixed in M2). The API's message:

> The compiled grammar is too large, which would cause performance issues. Simplify your tool schemas or reduce
> the number of strict tools.

- `messages.count_tokens` does **not** catch it: the same request body counted 4,743 tokens (HTTP 200). The
  counting endpoint validates schema keywords but does not compile the grammar, so only a message call reveals
  the limit.
- The gateway treats a 400 as non-retryable (`LLMRequestError(400)`), so every generator or reviser call with
  this schema would fail.
- M2 makes no generator call. Making §11.5's output compilable is a spec change for M3's plan, shipped as
  prompt-schema version 2 and verified by this dry-run before any scoring call (plan Deviation 33 and the M3
  carry-forward).

**The `minimum` probe is rejected**, as the counting endpoint answered:

> output_config.format.schema: For 'integer' type, property 'minimum' is not supported

The schemas never rely on such keywords (§11.6). The SDK's `transform_schema` would move the keyword into a
description, so the probe adds it after langchain built the request body (`schema_dry_run.probe_count_body`).

## Decision

- The schema dry-run (`llm/schema_dry_run.py`, `jobhunter schema-dry-run [--live]`) keeps the generator case
  and reports it failed (R7-3).
- The probe runs on `messages.count_tokens` (free), records `rejected`, `accepted` or `error:<code>`, reserves
  nothing and never gates `passed` (R7-2).
- On the fake transport the default run replays V4's live answers:
  - `schema_dry_run/claude-sonnet-5-5/67f413fd3374.sse` (the 400: status, error type and message only, with no
    request id, organisation or cf-ray header);
  - the three Opus streams under `schema_dry_run/claude-opus-5-5/`;
  - the probe's count answer at `count_tokens/claude-sonnet-5-5/c27f5ba679b9.json`.
- The fake run's `eval_runs` row ends `completed` with `passed = false`, the correct M2 state of prompt-schema
  version 1. `jobhunter schema-dry-run` prints this table and exits 1:

```
schema         model              result
generator      claude-sonnet-5-5  http_400
critic         claude-opus-5-5    passed
profile        claude-opus-5-5    passed
queries        claude-opus-5-5    passed
probe:minimum  claude-sonnet-5-5  rejected (count_tokens, http 400, informational)
```

- `.github/workflows/schema-dry-run-manual.yml` runs the same command with `--live` on a throwaway database.
  For version 1 it ends red for the same reason.
- `tests/integration/test_schema_dry_run.py` pins all of this on the recordings: the cases, the outcomes, the
  `eval_runs` row, the checks, `max_tokens` 2,000 and effort `low` on every message call, a stripped enum and a
  one-byte schema difference each failing their case, and the CLI.
