# V20: the real client address behind the proxy

This record covers the dev part (Task 16 and the devproxy check of Task 18). The Caddy part, the
compose test stack with network test N2 (§18.2), lands in M5.

## Assumption

Login throttling (`login_attempts.ip`, the `ip:<address>` lockouts) and `sessions.ip` use the real client
address, never the proxy's (spec §16.3, §22 V20). The api takes that address from `request.client.host`
alone. uvicorn's proxy headers middleware (`--proxy-headers --forwarded-allow-ips=<proxy address>`, uvicorn
0.54.0) replaces it with the `X-Forwarded-For` value only when the TCP peer is the trusted proxy (the devproxy
at `172.30.0.2`, §19.1), so a header sent by any other peer is ignored. Caddy overwrites the header with
`header_up X-Forwarded-For {remote_host}`, so a client cannot pass its own value through the proxy either.

## Method

Integration tests in `tests/integration/test_auth.py`, against the digest-pinned PostgreSQL container. Each
wraps the real api (`create_app`, edge included) in `uvicorn.middleware.proxy_headers.ProxyHeadersMiddleware`
with `trusted_hosts=["172.30.0.2"]`, the middleware that `--proxy-headers` installs, and sends requests
through httpx's ASGI transport with a chosen TCP peer address:

- `test_v20_dev_real_client_ip_through_trusted_proxy`: one failed login from peer `172.30.0.2` with
  `X-Forwarded-For: 203.0.113.7`, one from the untrusted peer `198.51.100.9` with the spoofed
  `X-Forwarded-For: 203.0.113.8`; then reads `host(ip)` of the `login_attempts` rows in order.
- `test_v20_dev_session_ip_is_the_real_client_ip`: a successful login from peer `172.30.0.2` with
  `X-Forwarded-For: 203.0.113.9`; then reads `host(sessions.ip)`.
- Without the middleware, `test_ip_lockout_after_five_failures` and `test_global_lockout_after_twenty_failures`
  show the peer address reaching the throttle directly: five failures of `198.51.100.10` lock out
  `ip:198.51.100.10`, and one failure from each of twenty addresses reaches the global lockout.

## Observed result

- The attempts record `["203.0.113.7", "198.51.100.9"]`: the trusted peer's header is used, and the untrusted
  peer's spoofed header is ignored (the peer address is recorded instead).
- The session from the trusted peer records `203.0.113.9`.
- The api code needs nothing proxy-specific: `routes.auth.client_ip` reads `request.client.host` and only
  normalises it (an IPv4-mapped IPv6 address becomes IPv4). A request without a usable address (no `client`,
  or a host that is not an IP address) is counted under `0.0.0.0`, one shared bucket, so it cannot escape the
  per-address throttle.

### Task 18: through the devproxy

Method: the dev stack (`deploy/compose.dev.yaml`; devproxy is Caddy with `deploy/Caddyfile.dev`, on
`devedge` and on `proxy` at `172.30.0.2`; the api runs `jobhunter api --proxy-headers --forwarded-allow-ips
172.30.0.2`). Two logins by hand with curl from the host to `http://localhost:8080/api/auth/login`, each with
`Origin: http://localhost:8080` and a spoofed `X-Forwarded-For`:

1. an unknown username with `X-Forwarded-For: 203.0.113.50`: answered 401;
2. the dev user, created with

   ```
   docker compose --env-file deploy/images.lock -f deploy/compose.dev.yaml \
     run --rm --no-deps -T api jobhunter user create --username devuser --password-stdin
   ```

   with its password and `X-Forwarded-For: 203.0.113.51`: answered 204.

Then `host(ip)` and `success` of `login_attempts`, and `host(ip)` of `sessions`, read as the bootstrap superuser:

```
docker compose --env-file deploy/images.lock -f deploy/compose.dev.yaml exec -T postgres \
  psql -U jobhunter_bootstrap -d jobhunter -At \
  -c "select host(ip), success from login_attempts order by id" -c "select host(ip) from sessions"
```

Observed:

- `login_attempts`: `172.18.0.1|f`, `172.18.0.1|t`; `sessions.ip`: `172.18.0.1`. `172.18.0.1` is the Docker
  gateway of `devedge`, the address Docker's port publishing connects to devproxy from. Neither spoofed value
  reached the database: Caddy replaced the header with `{remote_host}`, and uvicorn trusted it because the
  TCP peer was `172.30.0.2`.
- uvicorn's access log line (JSON, through the redacting root handler) shows the client as `172.18.0.1:0`.
- The cookie: `Set-Cookie: __Host-jh_session=…; Max-Age=2592000; Path=/; Secure; HttpOnly; SameSite=Strict`.

Dev cookie behaviour: the cookie is `Secure` although the dev origin is `http://localhost:8080`. This is
intended. Browsers treat `http://localhost` as a secure context and accept `Secure` cookies (and the `__Host-`
prefix) from it. M4's playwright scenarios verify the browser session; M0's smoke test (Task 21) proves the
backend's session handling only.

## Decision

- uvicorn runs with `--proxy-headers --forwarded-allow-ips 172.30.0.2` (through `jobhunter api`, ruling T18-b)
  in dev (Task 18) and with Caddy's fixed `proxy` network address in production (M5); no other peer is
  trusted. `jobhunter api` turns proxy headers off unless `--proxy-headers` is given (uvicorn's own default is
  on).
- The api reads the client address from `request.client.host` only; it never parses `X-Forwarded-For`
  itself.
- N2 (M5) repeats this through the real Caddy, from two client addresses, with and without a spoofed header.

## M5 Task 22: through Caddy on the compose test stack (N2)

Method: network test N2, `tests/stack/test_prod_network.py::test_client_ip_through_caddy`, on the compose test
stack (`deploy/compose.yaml` with `deploy/compose.test.yaml`, project `jobhunter-prodtest`, `JOBHUNTER_ENV=test`):

```
JOBHUNTER_STACK_PREBUILT=embedder uv run pytest -m stack -q -p no:cacheprovider tests/stack/test_prod_network.py
```

- The production Caddy (`deploy/caddy/site.caddy`, with `header_up X-Forwarded-For {remote_host}`) serves
  `localhost` with its internal CA (`deploy/Caddyfile.test`) at its fixed `edge` address `172.30.1.2`, and at
  `172.30.0.2` on `proxy`. The api runs `jobhunter api --proxy-headers --forwarded-allow-ips 172.30.0.2`.
- Two clients at known addresses on `edge`, the probes `probe1` (`172.30.1.11`) and `probe2` (`172.30.1.12`).
  Each runs `$PT run --rm -T probeN python -I -c <script>` and sends three logins. Each login is a TLS
  connection of its own to `172.30.1.2:443`, with SNI and `Host` `localhost` (stdlib `ssl`, verified against
  Caddy's internal root) and `Origin: https://localhost:8443`:
  1. a wrong password;
  2. a wrong password with `X-Forwarded-For: 203.0.113.9`;
  3. the right password.
- The egress rule `deploy/firewall/docker-user.nft` was loaded meanwhile (`sudo -n nft -f`; V21), so the
  client path through Caddy was also checked with the rule in place.
- Then `host(ip), success` of `login_attempts` in id order, and `host(ip)` of `sessions`, as the bootstrap role
  (`tests/support/prodstack.psql`).

Observed:

- Answers: `401`, `401`, `204` for each probe.
- `login_attempts`: `172.30.1.11|f`, `172.30.1.11|f`, `172.30.1.11|t`, `172.30.1.12|f`, `172.30.1.12|f`,
  `172.30.1.12|t`. Each attempt records the probe's own address, and the spoofed login records it too:
  Caddy replaced the header with the address it saw, and the api trusted the header only because the TCP peer
  was `172.30.0.2`. `203.0.113.9` appears nowhere.
- `sessions`: `172.30.1.11`, `172.30.1.12`, the address of the probe that logged in.
- Three logins per address stay inside the edge's limit (10 a minute per address, 100 in all; Task 21's
  `test_the_login_limit_through_caddy` shows the limit) and the throttle's lockout (5 failures per address).

Decision: V20 holds through the real Caddy. No change: the api reads `request.client.host` only, and trusts
`X-Forwarded-For` from `172.30.0.2` alone.
