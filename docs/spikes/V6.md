# V6: the PostgresSaver contract

## Assumption

`langgraph-checkpoint-postgres` 3.2.0 (`AsyncPostgresSaver`, with `langgraph` 1.2.15) works on a dedicated
autocommit pool, its `setup()` runs on an autocommit connection and is idempotent, a graph run with
`durability="sync"` resumes within one thread by re-running only the node that did not finish, and deleting a
thread for retention leaves every other thread intact (spec §3.3.3, §22 V6). Every run attempt gets a thread of
its own, `run-<run_id>-a<attempt_no>`, so no attempt ever resumes from another attempt's checkpoints.

## Method

Integration tests against the digest-pinned PostgreSQL container:

- `tests/integration/test_migrate.py::test_checkpointer_setup_is_idempotent` (Task 6): `setup_checkpointer` runs
  `AsyncPostgresSaver(conn).setup()` twice, on one autocommit connection (`autocommit=True`,
  `prepare_threshold=0`, `dict_row`) as the migrator role.
- `tests/integration/test_migrate.py::test_the_app_role_can_use_the_saver_on_the_migrated_tables` (Task 6): the
  app role writes and reads a checkpoint through `open_saver` (a pool of 1 to 4 autocommit connections).
- `tests/integration/test_checkpointer_v6.py::test_v6_resume_reruns_only_unfinished_node_and_thread_delete`: a
  two-node graph `a → b` compiled with `open_saver(app DSN)`, on the thread `thread_id(1, 1)` (`run-1-a1`). Node
  `b` raises on its first call. The test invokes with `durability="sync"`, expects the error, invokes again with
  input `None` on the same thread, and counts the node calls. It then runs a second thread `run-2-a1`, deletes the
  first with `adelete_thread`, and reads the latest checkpoint of both.
- `tests/integration/test_runs.py` runs the no-op collection graph (`graphs/collect/graph.py`) through
  `worker.runs.execute_run` with the saver: `test_happy_path_noop_run` finds a checkpoint on `run-<id>-a1`, and
  the resume tests run a new attempt on `run-<id>-a2`.

## Observed result

The API of the pinned versions is as the plan assumed.

- `setup()` is idempotent on an autocommit connection: it reads the highest version in `checkpoint_migrations`
  and applies only the later migrations, so the second call applies none.
- `ainvoke(..., durability="sync")` persists each step before the next one starts. After `b` raised, the second
  `ainvoke(None, config)` on the same thread resumed from the checkpoint written after `a`: `a` ran once, `b` ran
  twice, and the final state was `steps == ["a", "b"]` (the `operator.add` reducer did not see `a`'s update
  twice).
- `AsyncPostgresSaver.adelete_thread(thread_id)` deletes the thread's rows from `checkpoints`,
  `checkpoint_blobs` and `checkpoint_writes`; afterwards `aget_tuple` returns `None` for it, and the other thread's
  latest checkpoint is still there. The app role holds the rights this needs on the migrated tables.
- A finding beyond the plan: in `langgraph` 1.2.15, passing `durability` to a graph compiled **without** a
  checkpointer does not only warn (`` `durability` has no effect when no checkpointer is present. ``): with
  `durability="sync"` the run then fails with `AttributeError: 'AsyncPregelLoop' object has no attribute
  '_put_checkpoint_fut'`. With `durability=None` the same graph runs normally. (Checked with a scratch script on
  a one-node graph; the tests' gated graphs in `test_runs.py` are compiled without a checkpointer.)

## Decision

- `graphs.checkpointer.open_saver` stays as it is: an `AsyncPostgresSaver` on a pool of 1 to 4 autocommit
  connections (`prepare_threshold=0`, `dict_row`); `migrate` runs `setup()` on one autocommit connection.
- `worker.runs.thread_id(run_id, attempt_no)` names every attempt's thread; `begin_new_attempt` always moves a
  run to a new thread (`runs.current_thread_id`, `run_attempts.thread_id`), so a new attempt never reads an older
  attempt's checkpoints (it rebuilds progress from durable receipts, §3.3.3).
- `execute_run` invokes the graph with `{"configurable": {"thread_id": …}, "recursion_limit": 200}` and
  `durability="sync"` whenever the graph has a saver of its own, and with no `durability` otherwise (the finding
  above), so a graph without a checkpointer neither warns nor fails.
- Thread retention (§20.1) deletes an old attempt's thread with `adelete_thread`; a deletion touches no other
  thread.
