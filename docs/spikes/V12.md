# V12: a Message Batch on Haiku with generator schema C, through `BatchesClient`

## Assumption

Spec §22 V12 (L6664), §10.10 and §21.4; M3 Task 26:
- the batch path works against the live Message Batches API as the client and the item decision assume it
  (`llm/batches.py`, `scoring/batch_items.py`): the create through `BatchesClient.create`, the retrievals,
  the results stream and the workspace listing, in the shapes the SDK validates;
- Haiku compiles the real generator schema of prompt-schema version 2, candidate C (A3 §3.7), as Sonnet did
  (V4b, V4 "M3");
- an item's usage is present, a `custom_id` of the `t<target>_a<attempt>` pattern comes back as sent, and the
  listing carries `created_at` and `request_counts`;
- an errored item's type is the SDK's nested `error.error.type` (Carry T8-b);
- the batch params keep the cache marker (L6622): how the items' cache counts fall (§21.4 assumes a cold
  cache).

## Method

The spike `v12` (`scripts/spikes/v12_batches.py`) is the batch spike of the budgeted recorder
(`record_anthropic.py --spike v12 --dry-run`, then `--live --max-wait-hours 1.9`, on 2026-10-29). Its three
items, `t1_a1`, `t2_a1` and `t3_a1`, are the online generator request of three synthetic ads (V5's ads 1–3:
invented employers, no contact data), rendered by `render.score_prompt` from prompt-schema version 2 on one
synthetic profile (V5's profile 1), so the three share the prefix (the rubric v2 block and the profile block
with the cache marker, 18,957 bytes). The node is the seeded generator node with its model replaced by
`claude-haiku-5-5`: effort `medium`, `max_tokens` 6,000 (the first stage). The params are
`LLMGateway.batch_request_body` of each item (the online body without `stream`, the marker kept).

The recorder reserved the batch's worst case, the sum of its items' batch worst cases ($0.003189 + $0.003187
+ $0.003189 = $0.009565), as one entry before the create left (`SPIKE_CALLS["v12"] = 1`: one batch). It then
retrieved the batch every 60 s until it ended, streamed the results, settled the entry at batch prices from the
items' usage, and listed the workspace until it found the batch. Every exchange was written raw as it
completed. The committed documents keep no provider identity: the batch id is `msgbatch_v12_recorded`, each
message id `msg_v12_recorded_<custom_id>`, no `request_id`, the listing reduced to the spike's batch, and
each thinking block reduced to its shape (`[signature omitted]`; the API sent the thinking text empty).

## Observed result

**Timings.** Created at 01:39:36 UTC and `ended` at 01:46:05 (6 min 28 s); the poll saw it ended on its eighth
retrieval, 422 s after the create (seven `in_progress` retrievals first, `request_counts.processing = 3`
throughout). `expires_at` was the creation plus 24 h. The listing found the batch on its first page.

**The items** (all `succeeded`, none errored, canceled or expired):

| Item | Model served | Stop reason | Input | Cache creation | Cache read | Output (of it thinking) | Settled (batch) |
|---|---|---|---|---|---|---|---|
| `t1_a1` | `claude-haiku-5-5` | **`max_tokens`** | 1,792 | **8,644** | 0 | 6,000 (4,372) | $0.002130 |
| `t2_a1` | `claude-haiku-5-5` | **`max_tokens`** | 1,779 | 0 | **8,644** | 6,000 (4,116) | $0.001632 |
| `t3_a1` | `claude-haiku-5-5` | `end_turn` | 1,791 | 0 | **8,644** | 5,759 (3,356) | $0.001573 |

- **Haiku compiles schema C**: every item was answered (no `invalid_request_error`), and `t3_a1`'s output
  is a complete C document (16 facts, the six criteria) with no path outside the schema
  (`schema_dry_run.schema_violations`) that validates as the version's mirror.
- **Two of the three items stopped at `max_tokens`**. At effort `medium`, Haiku thought for 3,356–4,372 of
  its 6,000 output tokens, and the text of `t1_a1` and `t2_a1` was cut mid-JSON. The decision table sends
  such an item back online at the enlarged stage (`max_tokens_first_stage` → `pending('batch_max_tokens')`).
  The seeded generator is Sonnet, not Haiku; V5 measures Sonnet's and Opus's output at `medium`.
- **The cache was shared inside the batch.** The first item wrote the prefix (`cache_creation_input_tokens`
  8,644, all 5-minute), and the other two read it (`cache_read_input_tokens` 8,644 each). §21.4's cold-cache
  assumption is the conservative case: here only one item of three paid the write.
- **The cached part is 8,644 tokens** for 18,957 bytes of rubric and profile text, 0.456 tokens per byte.
  That is more than V19's largest ratios for M2's generator-shaped system blocks (0.363 and 0.450) would give
  for the two texts alone (about 7,380 tokens). If the version-2 rubric block tokenises like those, about
  1,260 more tokens sit in the cached part, which would fit the output schema's framing being placed before the
  system blocks (A3 G7). This is an inference, not a measurement: V5's pairs and its free `count_tokens`
  splits settle it.
- Each item's whole input was about 10,430 tokens (1,780–1,790 uncached + 8,644 cached) against a bound of
  26,992–27,019 (bytes plus `PROMPT_OVERHEAD_TOKENS`): 39% of it.
- **The documents** validate with the pinned SDK: the create and every retrieval as `MessageBatch`, every
  result line as `MessageBatchIndividualResponse`. The `custom_id`s came back as sent; the listing entry
  carries `created_at` and `request_counts` (`succeeded: 3`, the rest 0); `service_tier` is `batch`.
- **T8-b**: the batch had **no errored item**, so the nested `error.error.type` was not observed live. The
  fake's errored shape (`{"type": "errored", "error": {"type": "error", "error": {"type": …}}}`) stays as
  built; `test_v12_replay.py` exercises it on the fake's documents.

## Decision

- The batch path is verified against the live API, on Haiku with schema C. No code changes follow.
- The four documents are committed under `tests/contract/fixtures/anthropic/batches/v12/`: `create.json`,
  `retrieve.json` (the eight retrievals in order), `results.json` (the three result lines) and `list.json`.
  `tests/unit/test_v12_replay.py` replays the recorded lines through `batch_items.process_item` on a Haiku
  tuple of the test database: each succeeded item is billed at batch prices from its usage, the two
  `max_tokens` items included.
- Open for the controller: whether the batch generator's first-stage 6,000 tokens is enough at `medium` once
  V5 has measured Sonnet's output. On Haiku it was not enough for two items of three.
