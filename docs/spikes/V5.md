# V5 (local part): the stream idle timeout, and whether `ChatAnthropic` takes `anthropic.Timeout`

## Assumption

Spec §10.1 G3 and §22 V5: every Claude call uses `anthropic.Timeout(connect=10, read=120, write=30, pool=10)`,
an `httpx2` timeout object from the SDK, whose read value is the idle time between SSE events. The idle read
timeout fires at 120 s ± 5. If `ChatAnthropic` rejects the object, the gateway subclasses it and overrides its
async client factory (the G3 fallback). Plan Task 4 adds two questions: whether `ChatAnthropic` can use an
injected `httpx2` client, and which timeout the SDK honours, the one sent with each request or the http
client's own (pre-flight F23). The read timeout must be injectable for tests (C15 uses 2 s).

The 20 real streamed generator and critic calls of §22 V5 (p99 duration < 300 s, SSE pings < 30 s apart during
thinking) are M3's, where those nodes first call (plan Deviation 9). This part makes no paid call.

## Method

`tests/support/llm.LocalSSEServer` is an HTTP/1.1 server on `127.0.0.1:0` that answers with a synthetic SSE
stream, and can stall after its first event or before its response headers. The client reaches it through a
transport mounted on `https://api.anthropic.com` (`transport.make_http_client(cfg, mount=server.transport())`),
which forwards each request over plain HTTP with its headers unchanged. So the base URL stays the constant, the
server sees `Host: api.anthropic.com`, and each timeout is a real socket read timeout. The tests are in
`tests/integration/test_llm_transport.py`:

- `test_v5_the_production_idle_read_timeout_fires_at_120_s` (marked `slow`): `_chat(...)` on
  `make_http_client(cfg)` with the default timeout, against a stream that stalls after `message_start`. It ran
  once on 2026-10-21, together with a scratch run of the same call that also printed the request's `timeout`
  extension.
- `test_an_injected_one_second_read_timeout_fires_on_a_stalled_stream`: the same with
  `make_http_client(cfg, read_timeout_s=1.0)`.
- `test_the_sdk_sends_its_own_timeout_with_each_request`: a `GatewayChatAnthropic` whose SDK timeout has
  `read=1`, over an http client whose own timeout has `read=30`.
- `test_a_stall_before_the_response_headers_is_an_api_timeout_error`: the server never sends its headers.
- `test_v5_chat_anthropic_alone_takes_neither_the_sdk_timeout_nor_the_http_client`: the plain `ChatAnthropic`
  of `langchain-anthropic` 1.7.6, given the timeout object and then an `http_client`.

The sources read are `langchain_anthropic/chat_models.py` and `_client_utils.py` (1.7.6), and
`anthropic/_base_client.py` and `_client.py` (1.15.0).

## Observed result

| Case | Timeout that applies | Fired after | Exception raised by `ainvoke` (cause chain) |
|---|---|---|---|
| Stall after the first event, production timeout | read 120 s | **120.14 s** | `httpx2.ReadTimeout` ← `httpcore2` `ReadTimeout` ← `TimeoutError` |
| Stall after the first event, `read_timeout_s=1.0` | read 1 s | 1.02 s | the same |
| SDK timeout `read=1` over an http client `read=30` | read 1 s (the SDK's) | 1.01 s | the same |
| Stall before the response headers, `read_timeout_s=1.0` | read 1 s | 1.01 s | `AnthropicTimeoutError` ← `anthropic.APITimeoutError` ← `httpx2.ReadTimeout` |

- **The idle read timeout fires at 120.14 s**, within 120 s ± 5. The request's `timeout` extension was
  `{'connect': 10.0, 'read': 120.0, 'write': 30.0, 'pool': 10.0}`.
- **The SDK honours the timeout it sends with each request.** `AsyncAnthropic._build_request` passes
  `timeout=self.timeout` (or a per-call `timeout` option) to `http_client.build_request` for every request, and
  that sets the request's `timeout` extension, which the transport uses. The http client's own timeout is only
  the SDK client's default, and only when the SDK client gets no `timeout` and the http client's differs from
  httpx2's default. The third row shows it: the SDK's 1 s won over the http client's 30 s. The SDK also sends
  `x-stainless-read-timeout: 120.0` with each request (V13's capture).
- **A stall in mid-stream is not wrapped.** After the response headers, the SSE iteration raises
  `httpx2.ReadTimeout` itself: the SDK wraps transport errors only around `send`, and langchain wraps only
  `anthropic.APIError`. A stall before the headers happens inside `send`, so the SDK raises `APITimeoutError`,
  and langchain re-raises it as `AnthropicTimeoutError` (a subclass of `anthropic.APITimeoutError`).
- **langchain re-raises every SDK error as a subclass of it**, `from` the original
  (`_handle_anthropic_api_error`): for example `AnthropicRateLimitError(anthropic.RateLimitError)`,
  `AnthropicOverloadedError(anthropic.OverloadedError)` and `AnthropicConnectionError(anthropic.APIConnectionError)`.
  An `isinstance` check against the SDK class still holds. The transport's exception is the SDK error's
  `__cause__`, so it is two steps down the chain: `httpx2.ConnectError` for a refused connection.
- **`ChatAnthropic` 1.7.6 cannot take `anthropic.Timeout`.** Its `timeout` field (`default_request_timeout`) is
  typed `float | None`, and `ChatAnthropic(timeout=anthropic.Timeout(...))` raises a pydantic `ValidationError`
  (`float_type`).
- **`ChatAnthropic` 1.7.6 cannot use an injected http client.** It has no `http_client` field. One passed in
  gets `UserWarning: WARNING! http_client is not default parameter. http_client was transferred to
  model_kwargs`, and `model_kwargs` go into the request payload. It builds its async client itself, through the
  `lru_cache`d `_get_default_async_httpx_client(base_url, timeout, anthropic_proxy)`. That reads
  `ANTHROPIC_BASE_URL` when no base URL is given, and `ANTHROPIC_PROXY` through its `anthropic_proxy` field.
- A finding beyond the spike, in `httpx2` 2.13.1. With `trust_env` on (the default), the client turns
  `NO_PROXY` into mounts. `api.anthropic.com` is in this container's `NO_PROXY`, so it becomes the pattern
  `all://*api.anthropic.com`. That pattern's host is longer than the host of a user mount on
  `https://api.anthropic.com`, so it outranks the user mount and selects the default (network) transport
  instead. While the gateway was prototyped, one request with a dummy key went past an intended mock in this
  way. It reached the real API and was refused 401 `authentication_error`. It was not billed, and the real key
  was not involved.

## Decision

- **The G3 fallback is needed.** `gateway.GatewayChatAnthropic` subclasses `ChatAnthropic`:
  - It retypes the `timeout` field to `anthropic.Timeout` and adds an `http_client: httpx2.AsyncClient` field,
    which is not serialised.
  - It overrides the async client factory (`_async_client`) to build
    `anthropic.AsyncAnthropic(api_key=…, base_url="https://api.anthropic.com", timeout=…, max_retries=0,
    http_client=…, default_headers=…)`.
  - Its sync client raises.
  - A validator refuses any other base URL, `max_retries` other than 0, and an empty key (G1, G7).
- **One object carries the timeout.** `transport.make_http_client(cfg, *, read_timeout_s=120.0)` builds the
  client's timeout from `transport.TIMEOUT`, with only the read value overridable (`transport.http_timeout`).
  `gateway._chat` passes `timeout=http_client.timeout` to the SDK client, so the timeout sent with each request
  is the injected one. In prod, `make_http_client` refuses an injected read timeout or transport.
- **No client of the gateway can reach past its fake.** Whenever `make_http_client` replaces the API origin's
  transport (fake mode, or a `mount` from a test or the spike recorder), it sets `trust_env=False` and sends
  every other origin to a transport that raises `httpx2.ConnectError`. A fake or test client therefore never
  reaches the network (`tests/unit/test_fake_llm.py::test_fake_mode_never_reaches_the_network`). The production
  client keeps the environment's proxy settings.
- **The fake stall uses the same timeout.** `fake.RecordedSSETransport`'s `stall_after_first_event` waits for
  the request's own read timeout and then raises `httpx2.ReadTimeout`, as a socket read would. So C15's
  `make_http_client(..., read_timeout_s=2)` applies on the fake as it does on a socket.
- **For Task 5's error mapping:**
  - Catch the mid-stream `httpx2.TimeoutException` / `httpx2.TransportError` around `ainvoke` as a stream
    interruption, settled `ambiguous`, beside `anthropic.APITimeoutError` and `anthropic.APIConnectionError`.
  - For a connect failure before the send, look for `httpx2.ConnectError` in the cause chain.
- Open for M3 (Deviation 9): the 20 real streamed generator and critic calls at effort medium, measuring the
  p99 duration and the gaps between pings.

## M3: the 20 streamed calls through the gateway (V5's paid part, with V14's cache check)

### Assumption

Spec §22 V5 and V14 (M2 Deviation 9; M3 Task 26, Ruling T26-b): on the seeded policy, the generator
(`claude-sonnet-5-5`, schema C) and the critic (`claude-opus-5-5`, the §11.7.3 schema), both at effort
`medium` and streamed through `LLMGateway.call()`, finish within 300 s at p99, never leave 30 s between two SSE
events, and the second of two identical calls inside the 5-minute TTL reads at least 4,000 cached prefix
tokens. Open questions it may settle: A3 G6 (whether two schemas on one model and effort share a cache entry),
A3 G7 (whether the structured-output framing tokens are counted in the cached part or in `input_tokens`) and
A3 G28 (whether the first generator call pays a grammar compile).

### Method

The spike `v5` (`scripts/spikes/v5_stream_timing.py`, run as `record_anthropic.py --spike v5 --dry-run
--through-gateway`, then `--live --through-gateway`, on 2026-10-29 from 01:58 to 02:03 UTC) is a gateway spike
of the budgeted recorder: each call is `LLMGateway.call()` on a throwaway database (`tests/support`'s
PostgreSQL harness, migrated and seeded), as a non-scoring call of an `eval_runs` row of kind `canary`, with
the gateway's client sending through `BudgetedTransport(TimingTransport(network))`. Every HTTP attempt was
authorised and reserved before it left, against `SPIKE_CALLS["v5"] = 30` (the 20 calls and up to 10 enlarged
`max_tokens` stages, Ruling T26-c) and the $10.00 rule; the token split went to the free counting endpoint.

The 20 calls are 5 pairs `k`, sent one at a time in the order `g<k>a`, `g<k>b`, `c<k>a`, `c<k>b`. The two calls
of a pair are the same request, the second sent as soon as the first settled. Each pair has its own synthetic
profile and ad, so its first calls start cold, and the generator and the critic of a pair share the prefix:
`system[0]` the rubric block of rubric v2, `system[1]` the `<candidate_profile>` block with the one cache
marker, then `system[2]` the role's template and the user turn (`score_prompt` of prompt-schema version 2).
The requests are the gateway's own: `output_config` with the stored wire schema and `effort: medium`,
`max_tokens` 6,000 at the first stage (12,000 at the second), and `thinking: {type: adaptive, display:
summarized}`, which langchain-anthropic adds for both models when `reasoning_effort` is set. The dry run
checked all 20 payloads offline first (`payload ok` x20, worst $3.975296 for one attempt each, an enlarged
attempt at most $0.390810).

Per attempt, `TimingTransport` stamped every chunk with a monotonic clock; `attempt_timing` gives the time to
the first SSE event, the largest gap between two events, the usage, the stop reason, the `max_tokens` stage
and the thinking tokens (`usage.output_tokens_details.thinking_tokens`); per call, `call_s` runs from the
gateway call to its settled result. After the 20 calls, free `count_tokens` requests split the first generator
and critic requests into their components (the V19 method: the whole request, then each component alone as
the one user message; the framing is the whole minus the sum).

**G7: the framing is in the cached part.** The cached part of each first call is the prefix plus the schema
plus the framing, to 11 tokens: 7,423 + 737 + 473 + 11 = 8,644 for the generator, 7,423 + 424 + 310 + 11 =
8,168 for the critic. The uncached `input_tokens` are the components after the marker, less the same 11:
614 + 1,189 - 11 = 1,792 and 835 + 2,670 - 11 = 3,494. So the schema and its framing are counted in
`cache_creation_input_tokens` on a cold call and in `cache_read_input_tokens` on a warm one, not in
`input_tokens`. The framing depends on the schema (473 tokens for C, 310 for the critic's), and the 476 tokens
between the two roles' entries are exactly the schema difference (313) plus the framing difference (163);
both models count the rubric and the profile identically, so the difference is not a tokenizer's.

**G6, by inference only.** Since a request's schema and framing lie inside its cached part, before the one
cache marker, a request with another schema has another prefix up to that marker, and a cache entry is read
only by an identical prefix. Two schemas on one model and effort therefore should not share an entry. V5 cannot
observe it, because its two schemas run on two models; V14's `g6`/`x6` pair (the critic schema on Sonnet after
the generator on the same prefix) would observe it, and is not run here.

### Decision

- **V5's acceptance is met** at prompt-schema version 2 and the seeded policy: p99 22.5 s against 300 s, gaps at
  most 5.31 s against 30 s, and every second call of a pair read 8,104 or more cached tokens against 4,000.
  The 120 s idle read timeout of the local part leaves a margin of more than 20 times the largest gap.
- **The prefix cache works through the gateway**: the first call of a prefix writes one entry (the prefix with
  the schema and its framing, G7), and the next identical call inside the TTL reads all of it. The critic on
  Opus writes its own entry; it never reads the generator's.
- **G7 is answered**: the framing tokens and the schema are in the cached part. A cost estimate that prices
  the prefix at the cache rates must include the schema and its framing in it (the generator's cached part is
  8,580 to 8,792 tokens here, not the 7,423 of the rubric and the profile).
- **G6 is answered by inference only**: no sharing between two schemas. Whether to observe it directly with
  V14 is the controller's call.
- **G28 stays open**: no cold grammar was met.
- The recordings are committed: every stream as `<purpose>/<model>/<schema12>.<case>.sse` with its sidecars
  (`generate/claude-sonnet-5-5/7d5369246e82.g<k><a|b>`, `critic/claude-opus-5-5/cf6a3209541a.c<k><a|b>`), and,
  where the dev stack's fake finds them (Carry T8-c), `g1b` as `generate/claude-sonnet-5-5/7d5369246e82.sse`,
  `c1b` as `critic/claude-opus-5-5/cf6a3209541a.sse`, and `g1b` again as
  `revise/claude-sonnet-5-5/7d5369246e82.sse` (sidecar `purpose: generate`, `serves: revise`; the reviser has
  the generator's model and schema). Every critic stream's thinking is replaced by `[thinking omitted]` and its
  signature by `[signature omitted]`; the PII gate passes.
