# V1: deferring a procrastinate job inside the caller's transaction

## Assumption

procrastinate 3.10.0 can insert a job through the caller's own SQLAlchemy/psycopg connection, so that the job
commits or rolls back together with the caller's writes (spec §3.3.2, §22 V1). A queueing lock that is already
taken must not poison the caller's transaction.

## Method

Integration tests in `tests/integration/test_queue.py`, against the digest-pinned PostgreSQL container:

- `test_v1_rollback_leaves_no_job`: defer inside a transaction, roll it back, count the jobs.
- `test_v1_commit_leaves_exactly_one_job`: defer inside a transaction, commit, count the jobs; `live_job_exists`
  finds the job by its arguments and not another one.
- `test_already_enqueued_keeps_caller_transaction_usable`: defer twice with the same queueing lock in one
  transaction, then run another statement in it and commit.
- `test_defer_in_tx_needs_no_open_app`: defer through a task app that was never opened.

## Observed result

The API of 3.10.0 is as the plan assumed; no adaptation was needed.

- `Task.configure(connection=...)` (`ConfigureTaskOptions.connection`) makes the job insert run on an external
  connection instead of the connector's pool. `PsycopgConnector` implements it as
  `execute_query_all_async_with_connection`, which opens a cursor on the given psycopg `AsyncConnection`.
- The connection is `(await conn.get_raw_connection()).driver_connection` of the SQLAlchemy `AsyncConnection`.
  It is the connection that carries the caller's transaction, so the insert commits or rolls back with it.
- It needs no open app and no pool: `test_defer_in_tx_needs_no_open_app` defers through `make_queue_app(dsn)`
  without `open_async()`, checks the job count, and checks that the app's own pool stayed closed.
- Rollback leaves 0 jobs; commit leaves exactly 1.
- A taken queueing lock raises `procrastinate.exceptions.AlreadyEnqueued` (the connector turns the unique
  violation of the partial index `procrastinate_jobs_queueing_lock_idx_v1`, which covers jobs in `todo` only).
  It is procrastinate's own exception, not a SQLAlchemy `DBAPIError`. The failed insert aborts the PostgreSQL
  transaction, so without a savepoint the caller's next statement fails with `InFailedSqlTransaction`; this was
  checked by removing the savepoint, which makes the third test fail on its `SELECT 1`.
- Inside `conn.begin_nested()`, `AlreadyEnqueued` rolls back the savepoint only. `defer_in_tx` catches it
  outside the savepoint block and returns `None`; the caller's transaction stays usable and its earlier job
  stays.

## Decision

`jobhunter.worker.tasks.defer_in_tx(conn, task, *, lock, queueing_lock, **kwargs)` defers through the caller's
connection, in a savepoint, and returns the job id or `None` for a taken queueing lock. Any other error leaves
the savepoint and propagates.

Correctness does not rest on it (§3.3.2): every mutation that needs follow-up work also writes a durable
`operations` or `runs` row in the same transaction, and the reconcilers re-defer a pending one that has no live
job (`live_job_exists`). The reconciler half of the V1 acceptance criterion (a lost job is re-deferred within
2 minutes) is asserted with those reconcilers, which are registered by the tasks that own `queued_runs` and
`operations`.
