# V22: secret delivery and the non-superuser restore

## Assumption

On the production compose, every service reads its secrets from files `root:10010`, mode 0440, and a backup
set restores without a superuser: `pg_restore --no-owner --no-acl --exit-on-error` with the filtered list
(`backup.restore.restore_list`) as the migrator into the application database, and as `jobhunter_restore`
into a database created from `jobhunter_template`; the replay of a manifest stream newer than the set then
completes, and both `restore verify` phases pass (spec §19.2, §19.5, §22 V22; plan M5 Task 26).

## Method

The compose test stack (`PT`, site A) and its restore target (`PB`, site B, the same files under project
`jobhunter-prodtest-b`), with the S3 stand-in (`jobhunter-s3stub`, versitygw) as the one restic repository of
both sites. The secret files are `scripts/test-secrets.sh`'s dummies. One sequence, in order:

    docker compose --env-file deploy/images.lock -f deploy/compose.dev.yaml -f deploy/compose.fixtures.yaml \
      -f deploy/compose.fakellm.yaml -f deploy/compose.e2e.yaml down
    JOBHUNTER_STACK_PREBUILT=embedder uv run pytest -m stack -q -p no:cacheprovider \
      tests/stack/test_prod_restore.py

The restore itself is the `restore` service's command, run as an operator runs it:
`docker compose … -p jobhunter-prodtest-b --profile restore run --rm restore` (`jobhunter restore run`), after
`up -d postgres` on an empty `pgdata`; the phase after the replay is checked again with
`jobhunter restore verify --set <id> --phase replayed` in a restore container; the monthly restore test with
`jobhunter backup restore-test` in the backup container. Every log line read is a JSON event of the app's own
(ids, steps, codes, counts; key ids as hex ids). No secret value, password or key is in this document.

Observations that shaped the code:

- A replayed manifest the dump lacks is inserted under a new row id on the restored site: its stream identity
  is its `manifest_uuid`, and the stack test reads it by that.
- One repository serves every site, so "the latest manifest stream" a restore takes is the latest any site
  shipped (in the C39 restore, B's stream from C37, with A's restored manifests in it). Replaying manifests of
  another site's history is harmless: their selectors are bounded by their `max_ids`, and the restored site's
  identities advance above every bound.
- The restore container holds no data key: the set's `data_key_ids` are logged as hex ids
  (`restore_set_staged`) for the operator's `crypto rotate` passes (Task 28).
