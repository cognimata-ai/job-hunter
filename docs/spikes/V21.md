# V21: the no-egress boundary

This record covers the dev part (Task 18): the compose networks of `deploy/compose.dev.yaml`. The part on the
target VPS image, with the `DOCKER-USER` rule (`deploy/firewall/docker-user.nft`, §16.9) installed and with
`docparse` (`network_mode: none`), is the compose test stack's network test N1 (§18.2) in M5.

## Assumption

The api has no route to the internet: both of its networks, `proxy` and `internal`, are `internal: true`
bridges, so its container has no default route and Docker's embedded DNS resolves only the names on those
networks (spec §3.1, §19.1, §22 V21). The worker reaches the outside through its third network, `egress`, a
plain bridge. Only devproxy is published, on `127.0.0.1:8080`, through its own network `devedge`.

## Method

Stack test `tests/stack/test_dev_stack.py::test_v21_dev_api_has_no_egress_but_worker_does` (marker `stack`,
run with `uv run pytest tests/stack/test_dev_stack.py -m stack -q`). The fixture brings the stack up with
`docker compose --env-file deploy/images.lock -f deploy/compose.dev.yaml up -d --build --wait`. It then starts
a probe container `jh-egress-probe` (the digest-pinned python image running `python -m http.server 8099`) on
`jobhunter-dev_egress`, a network the api is not attached to. Each probe is a 3 s `socket.create_connection`
run with `docker compose exec` inside the service, with exit status 0 (connected) or 1 (`OSError`):

- worker → `jh-egress-probe:8099`: must connect (retried for up to 15 s while the probe starts);
- api → `postgres:5432`: must connect. This is the control: it shows that the probe runs in the api container
  and that the two failures below come from the network, not from a failed `exec`;
- api → `1.1.1.1:443` and api → `jh-egress-probe:8099`: must fail.

The same probes were also run by hand against the running stack, with the error class and errno printed, and
each container's routing table was read from `/proc/net/route`.

## Observed result

The stack test passes (8 of 8 in the module). By hand:

| Probe | From `api` (`proxy`, `internal`) | From `worker` (`internal`, `egress`) |
|---|---|---|
| TCP `1.1.1.1:443` | fails: `OSError` errno 101, *Network is unreachable* | connects |
| DNS `pypi.org` | fails: `gaierror` −3, *Temporary failure in name resolution* | resolves |
| TCP `jh-egress-probe:8099` | fails: the name does not resolve (`gaierror`) | connects |
| DNS + TCP `postgres:5432` | connects | connects |
| Routes | the two on-link subnets only, no default route | on-link subnets plus a default route via the `egress` gateway |

- Internet reachability from the worker is **not asserted**. In this dev container outbound traffic goes
  through the agent proxy, so a successful outside connection says nothing about a production host. The test
  asserts only what the dev stack itself guarantees: the worker reaches a container on `egress`, and the api
  reaches neither that container nor an outside address.
- DNS behaviour for outside names (whether an internal network's resolver forwards queries) and the
  `DOCKER-USER` rule are verified on the target VPS image in M5 (N1). Here the api's lookup of an outside name
  failed, which is what an internal-only container should see, but the dev container is not the target host.
- Addresses: devproxy holds the fixed `172.30.0.2` on `proxy`, and the api was given `172.30.0.128`.

### Finding: the fixed proxy address needs a dynamic range that excludes it

Docker assigns dynamic addresses from the bottom of a subnet: a container started on a fresh
`172.31.250.0/24` network got `.2`. The api starts before devproxy (devproxy waits for the api to be healthy),
so with only `subnet: 172.30.0.0/24`, as in §19.1, the api would take `172.30.0.2` and devproxy could not
start. The dev compose file therefore sets `ip_range: 172.30.0.128/25` (and `gateway: 172.30.0.1`) on
`proxy`: dynamic addresses come from the upper half only. The production compose file (M5) needs the same, since
its caddy also waits for a healthy api.

## Decision

- The api keeps `proxy` and `internal` only, both `internal: true`; only the worker is on `egress`
  (M0 has no backup or restore service yet).
- `proxy` uses `subnet: 172.30.0.0/24`, `ip_range: 172.30.0.128/25`, `gateway: 172.30.0.1`; devproxy (dev) and
  caddy (M5) take the fixed `172.30.0.2`, the only forwarder the api trusts.
- N1 in M5 repeats the probes on the target VPS image with the `DOCKER-USER` rule installed, adds DNS queries
  and `docparse`, and asserts internet reachability from the worker there.
