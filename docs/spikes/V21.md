# V21: the no-egress boundary

This record covers the dev part (Task 18): the compose networks of `deploy/compose.dev.yaml`. The part on the
target VPS image, with the `DOCKER-USER` rule (`deploy/firewall/docker-user.nft`, §16.9) installed and with
`docparse` (`network_mode: none`), is the compose test stack's network test N1 (§18.2) in M5.

## Assumption

The api has no route to the internet: both of its networks, `proxy` and `internal`, are `internal: true`
bridges, so its container has no default route and Docker's embedded DNS resolves only the names on those
networks (spec §3.1, §19.1, §22 V21). The worker reaches the outside through its third network, `egress`, a
plain bridge. Only devproxy is published, on `127.0.0.1:8080`, through its own network `devedge`.

## Method

Stack test `tests/stack/test_dev_stack.py::test_v21_dev_api_has_no_egress_but_worker_does` (marker `stack`,
run with `uv run pytest tests/stack/test_dev_stack.py -m stack -q`). The stack test runs the dev compose file
as a compose project of its own, `jobhunter-stacktest`, so it never touches the normal dev stack
`jobhunter-dev` or its database (ruling T21-g). Every compose call it makes starts with
`docker compose -p jobhunter-stacktest --env-file deploy/images.lock -f deploy/compose.dev.yaml`
(written `<compose>` below), and it removes only that project's containers, networks and volumes. When
`jobhunter-dev` has a running container or a network (the fixed subnet and port 8080 would collide), the
module is skipped with a message; it never stops or removes anything of `jobhunter-dev`.

The fixture brings the stack up with `<compose> up -d --build --wait`. It then starts a probe container
`jobhunter-stacktest-egress-probe` (the digest-pinned python image running `python -m http.server 8099`) on
`jobhunter-stacktest_egress`, a network the api is not attached to. Each probe is a 3 s
`socket.create_connection` run inside the service with `<compose> exec -T <service> python -c …`, with exit
status 0 (connected) or 1 (`OSError`):

- worker → the probe on port 8099: must connect (retried for up to 15 s while the probe starts);
- api → `postgres:5432`: must connect. This is the control: it shows that the probe runs in the api container
  and that the two failures below come from the network, not from a failed `exec`;
- api → `1.1.1.1:443` and api → the probe on port 8099: must fail.

The same probes were also run by hand against the running stack, with the error class and errno printed, and
each container's routing table was read from `/proc/net/route`.

## Observed result

The stack test passes (8 of 8 in the module). These results were recorded before ruling T21-g, when the
stack test still ran as `jobhunter-dev` with the probe `jh-egress-probe` on `jobhunter-dev_egress`; the
networks and the probes are the same. By hand:

| Probe | From `api` (`proxy`, `internal`) | From `worker` (`internal`, `egress`) |
|---|---|---|
| TCP `1.1.1.1:443` | fails: `OSError` errno 101, *Network is unreachable* | connects |
| DNS `pypi.org` | fails: `gaierror` −3, *Temporary failure in name resolution* | resolves |
| TCP `jh-egress-probe:8099` | fails: the name does not resolve (`gaierror`) | connects |
| DNS + TCP `postgres:5432` | connects | connects |
| Routes | the two on-link subnets only, no default route | on-link subnets plus a default route via the `egress` gateway |

- Internet reachability from the worker is **not asserted**. In this dev container outbound traffic goes
  through the agent proxy, so a successful outside connection says nothing about a production host. The test
  asserts only what the dev stack itself guarantees: the worker reaches a container on `egress`, and the api
  reaches neither that container nor an outside address.
- DNS behaviour for outside names (whether an internal network's resolver forwards queries) and the
  `DOCKER-USER` rule are verified on the target VPS image in M5 (N1). Here the api's lookup of an outside name
  failed, which is what an internal-only container should see, but the dev container is not the target host.
- Addresses: devproxy holds the fixed `172.30.0.2` on `proxy`, and the api was given `172.30.0.128`.

### Finding: the fixed proxy address needs a dynamic range that excludes it

Docker assigns dynamic addresses from the bottom of a subnet: a container started on a fresh
`172.31.250.0/24` network got `.2`. The api starts before devproxy (devproxy waits for the api to be healthy),
so with only `subnet: 172.30.0.0/24`, as in §19.1, the api would take `172.30.0.2` and devproxy could not
start. The dev compose file therefore sets `ip_range: 172.30.0.128/25` (and `gateway: 172.30.0.1`) on
`proxy`: dynamic addresses come from the upper half only. The production compose file (M5) needs the same, since
its caddy also waits for a healthy api.

## Decision

- The api keeps `proxy` and `internal` only, both `internal: true`; only the worker is on `egress`
  (M0 has no backup or restore service yet).
- `proxy` uses `subnet: 172.30.0.0/24`, `ip_range: 172.30.0.128/25`, `gateway: 172.30.0.1`; devproxy (dev) and
  caddy (M5) take the fixed `172.30.0.2`, the only forwarder the api trusts.
- N1 in M5 repeats the probes on the target VPS image with the `DOCKER-USER` rule installed, adds DNS queries
  and `docparse`, and asserts internet reachability from the worker there.

## M5 Task 22: the compose test stack in the dev container (N1, local part)

This part ran in the dev container. The part on the target VPS image, including the outside reach from the
worker, stays the deployment step's.

Method: network test N1, `tests/stack/test_prod_network.py` (marker `stack`), on the compose test stack
(`deploy/compose.yaml` with `deploy/compose.test.yaml`, project `jobhunter-prodtest`):

```
JOBHUNTER_STACK_PREBUILT=embedder uv run pytest -m stack -q -p no:cacheprovider tests/stack/test_prod_network.py
```

- **The rule.** The egress rule is `deploy/firewall/docker-user.nft` (Deviation 35). It is a table of its own,
  `inet jobhunter_egress`, with a `forward` chain at priority -10 that drops new connections from `proxy`,
  `internal` and `edge` to any address outside 172.30.0.0/16; `egress` and Caddy's `172.30.1.2` are excepted.
  The test loads it with `sudo -n nft -f` and deletes it with `sudo -n nft delete table inet jobhunter_egress`
  after each test, after a failure too. No other table is touched.
- **The probes.** A python script prints what it sees: a name resolved (`getaddrinfo`), a TCP connection (3 s
  time-out), and the interfaces. It runs in the services with `$PT exec -T <service> python -I -c …`, and on
  the test bridge in a new unprivileged container of the pinned python image.

Observed (6 passed, 1 skipped):

| Test | Result |
|---|---|
| `api`, without and with the rule | `example.com` and `stubsvc` (on `egress`) do not resolve: `gaierror` −3. TCP `192.0.2.1:443` and `1.1.1.1:443` fail at once: `OSError` errno 101, *Network is unreachable* (no route out). Control: `postgres` resolves to its `internal` address and `postgres:5432` connects. |
| `docparse`, without and with the rule | Its only interface is `lo`. `example.com` does not resolve (`gaierror` −3), and TCP `192.0.2.1:443` and `1.1.1.1:443` fail with errno 101. |
| The drop rule | A probe on a routable test bridge `jobhunter-prodtest-fenced` (172.30.250.0/24), which a test copy of the rule fences, tries TCP `192.0.2.1:443`: the attempt times out, and the drop statement's counter rises. The same attempt from the worker's `egress` address leaves the counter as it was. Without that bridge in the copy, the same attempt was refused at once (a mutation run), so the time-out is the rule's drop. |
| The worker, with the rule | `stubsvc` resolves to its `egress` address (172.30.3.0/24), and `GET http://stubsvc:8099/_log` answers 200. |
| The worker's outside reach | Skipped: it runs with `JOBHUNTER_N1_OUTSIDE=1` (CI, the VPS). Outbound traffic from the dev container goes through the agent proxy, so a connection out proves nothing here (the dev record above). |
| A reload | Loading the rule twice gives the same table: one chain and its three rules, not six. The host's other nft tables are unchanged. |

- The `edge` probes reached Caddy with the rule loaded (N2, V20), so the rule leaves the inbound path alone.
- A mutation run checked the reload test: with the file's `delete table` line removed, a second load appends
  three more rules, and the test fails.

Decision: the local part of N1 holds, with and without the rule. On the VPS, the rule is loaded at boot by
`deploy/firewall/jobhunter-egress.service` (before `docker.service`; `scripts/host-setup.sh` installs it).
There N1 runs with `JOBHUNTER_N1_OUTSIDE=1`, so the worker's outside reach is asserted too.
