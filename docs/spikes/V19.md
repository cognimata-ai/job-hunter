# V19: the text input bound, the prompt overhead and the native-PDF bound

## Assumption

Spec §22 V19, §10.7 and §1.5 S3 (chair decision C1).

- A text reservation bounds its input by `Σ utf8_bytes(component) + PROMPT_OVERHEAD_TOKENS[model]`. That holds
  if the tokenizer emits at most one token per UTF-8 byte for every rendered component (system blocks, messages,
  the `output_config` schema), German text with umlauts, `ß`, typographic quotes and dashes included.
- `PROMPT_OVERHEAD_TOKENS[model]` is twice the largest framing overhead measured: a whole request's tokens minus
  the sum of its components' tokens, each counted on its own.
- A native PDF reserves `ceil(1.25 × count_tokens) + PROMPT_OVERHEAD_TOKENS[model]`. Its path stays disabled
  unless a recorded native-PDF usage is at most 1.25 × its count.
- Afterwards, §6.9.1's overrun-buffer bound of the seeded settings must not exceed their `overrun_buffer_usd`.

## Method

`scripts/spikes/v19_token_bound.py`, on 2026-10-21. Its pure analysis is pinned by
`tests/unit/test_v19_analysis.py`.

- **The corpus.** 32 synthetic requests per model, for each of the four models: 4 kinds × German and English × 4
  sizes. Each is 3,844 to 30,424 bytes, and none names a person or holds contact data. The kinds:
  - the profile extraction (`render.extract_profile_prompt`);
  - the query proposal (`render.propose_queries_prompt`);
  - generator-shaped and critic-shaped requests in the §10.6 layout: the rubric v1 block, the cached
    `<candidate_profile>` block, the role instructions, then the `<job_ad>`, the critic's with a `<draft>`.

  They use the four transformed schemas of prompt-schema version 1.
- **Counting** with `messages.count_tokens` (free), through the gateway (`LLMGateway.count_body` and
  `count_tokens`, `record_anthropic.counting_gateway`):
  - the whole request as the gateway sends it (effort `medium`, langchain's adaptive `thinking`, the cache
    marker of the generator- and critic-shaped requests);
  - every component on its own, as the one user message of a request.

  That made 301 count requests, none of them a message. A component's own count includes that request's
  minimal framing. The `tokens ≤ bytes` check is then stricter, and the bound stays sound: the same counts feed
  both the check and the framing.
- **Recorded usages.** Every recorded usage of Tasks 4 and 7 (V13 ×2, V4 ×3, the native PDF) was compared with
  its bound under the new constants. The bound is computed from the raw request captures.
- **The native PDF.** One paid extraction through the recorder, after its `--dry-run`:
  - a synthetic one-page PDF 1.4 (1,041 bytes, Helvetica text of a CV without name or contact data,
    `v19_token_bound.minimal_pdf`);
  - `render.extract_profile_native_pdf_prompt` on `claude-opus-5-5`, effort `low`, `max_tokens` 1,024, the
    profile schema;
  - `count_tokens` of the exact request first. The recorder's request, built offline, was checked to be exactly
    the counted body.
  - The reservation was `pricing.worst_case_usd(model, input_tokens_bound=native_pdf_bound(model, count),
    max_tokens=1024, extra_usd=native_pdf_extra_usd(0.50))`, with the extra share at the §13.1 minimum buffer
    ($0.125).

## Observed result

**Tokens ≤ bytes holds for every component** (§1.5 S3 stands; no §10.7 factor applies). The largest
tokens-per-byte ratio of any component is **0.522** (12/23). Largest ratios by component, alike on all four
models:

| Kind | `system[0]` | `system[1]` | `system[2]` | `messages[0]` | schema |
|---|---|---|---|---|---|
| profile | 0.353 | | | 0.521 | 0.422 |
| queries | 0.321 | | | 0.472 | 0.423 |
| generator-shaped | 0.363 | 0.450 | 0.372 | 0.522 | 0.443 |
| critic-shaped | 0.363 | 0.450 | 0.300 | 0.505 | 0.445 |

A whole request is at most 0.493 tokens per byte of its components (927/1,880).

**The framing overhead** (whole minus the components) is the same at every size and in both languages. It is
also identical on all four models, which count alike. It follows the size of the output schema:

| Kind | Schema bytes | Framing overhead (tokens) |
|---|---|---|
| queries | 414 | 201 |
| critic-shaped | 952 | 311 |
| profile | 2,906 | 939 |
| generator-shaped | 5,621 | **1,320** |

**The new constants** (`backend/src/jobhunter/llm/bounds.py`, the V19 block):

| Model | `PROMPT_OVERHEAD_TOKENS` |
|---|---|
| `claude-opus-5-5` | **2,640** |
| `claude-sonnet-5-5` | **2,640** |
| `claude-haiku-5-5` | **2,640** |
| `claude-fable-5-1` | **2,640** |

That is `max(PROMPT_OVERHEAD_FLOOR = 1,000, 2 × 1,320)`. The floor is kept as a lower limit; V19 measured above
it on every model.

- **Every corpus request is within its new bound.** The smallest margin is 4,835 tokens.
- **Every recorded usage is within its bound** with the new constants:

| Recording | Used (input + cache) | Bound now |
|---|---|---|
| V13 Sonnet / queries schema | 741 | 3,975 |
| V13 Opus / queries schema | 741 | 3,975 |
| V4 critic / Opus | 1,898 | 6,261 |
| V4 profile / Opus | 2,588 | 6,534 |
| V4 queries / Opus | 1,058 | 4,754 |
| V19 native PDF / Opus | 6,152 | 10,330 (`native_pdf_bound`) |

`count_tokens` equalled the billed input exactly for each V4 case (1,898, 2,588, 1,058) and for the native PDF
(6,152).

**The native PDF:**
- `count_tokens` 6,152.
- 200 `end_turn`, usage 6,152 input (no cache) and 778 output.
- 6,152 ≤ 1.25 × 6,152, so **`NATIVE_PDF_ENABLED = True`**: §12.7's native path is allowed (Tasks 9, 13 and 14
  honour the flag).
- The response is committed as `tests/contract/fixtures/anthropic/v19_native_pdf/claude-opus-5-5/b6d87b4cbb17.*`.
  It has its own directory, because Task 13 owns `extract_profile`'s fixture key. Its sidecar holds
  `native_pdf_count_tokens`, and `tests/payload/test_recorded_bounds.py` checks it against `native_pdf_bound`.

**The §6.9.1 overrun-buffer bound** of the seeded settings, with the new constants:
- 3 score and 2 auxiliary online slots at the policy's costliest bound price: Opus, 2,640 × $5.00 per MTok.
- `batch_max_items` batch slots of the generator model at batch prices: Sonnet, 2,640 × $1.25 per MTok.
- The result is divided by 1e6 and rounded up to the cent.

| `batch_max_items` | Bound | Against the $2.00 default |
|---|---|---|
| 1,000 (spec rev 3.3 default) | (66,000 + 3,300,000) / 1e6 = **$3.37** | above: the task's stop rule ended it BLOCKED |
| **500** (spec rev 3.4 default, the user's decision) | (66,000 + 1,650,000) / 1e6 = **$1.72** | within |

With 1,000 batch items the measured overhead put the bound above the $2.00 default. The task stopped and
reported, changing no validation, default or batch size. The user chose a default `scoring.batch_max_items` of
**500**, keeping the 200–10,000 range (spec revision 3.4, plan Deviation 34). `settings_v1.json` holds 500, and
`tests/unit/test_v19_analysis.py` guards the bound against the seeded buffer until Task 15's
`test_seed_defaults_validate` takes over.

The largest framing comes from the generator-shaped requests, whose §11.5 schema the API rejects (V4,
`docs/spikes/V4.md`, plan Deviation 33). M3's compilable generator schema will change it, and V19's counting
can then be run again for free (`--count`, `--analyse`).

## Decision

- `PROMPT_OVERHEAD_TOKENS` is 2,640 for every model, and `NATIVE_PDF_ENABLED` is `True`
  (`v19_token_bound.py --analyse` wrote both).
- S3's residual assumption holds on the corpus as stated, so no byte factor is needed.
- The default `batch_max_items` is 500.

## M3 re-count

M3 Task 4, on 2026-10-26: the same analysis over a corpus whose generator and critic requests are the ones M3
sends (R12). No message was sent, so the paid-spike budget is unchanged.

**What changed in the corpus.** The score requests are now rendered by `render.score_prompt` from
prompt-schema version 2 (`v19_token_bound.V2`, built offline from `prompt_schema_v2()`), as the score nodes
render them. There are 8 generator, 8 critic and 8 reviser requests per model, one per language and size; the
reviser's were added in Task 4's fix round 1, so all three score roles are measured.
- `system[0]`: the shared rubric block of rubric v2;
- `system[1]`: the `<candidate_profile>` block, with the cache marker;
- `system[2]`: the role template;
- the user turn: the `<job_ad>` block (`render.job_ad_block`). For the critic it is followed by `<draft>`,
  `<required_facts>` and `<validator_issues>`, and for the reviser by `<previous_draft>` and `<issues>`.

The generator's and the reviser's schema is candidate C (`GeneratorWire`, 1,713 bytes), and the critic's is
the §11.7.3 schema. The profile and query requests are unchanged. That is 40 requests per model, 3,844 to
36,680 bytes each.

**The commands.** There were three, because the flags are a mutually exclusive group:
- `uv run python scripts/spikes/v19_token_bound.py --count`, with `JOBHUNTER_ANTHROPIC_API_KEY` set for the
  counting endpoint only. It sent 152 `count_tokens` requests (free); the unchanged profile and query requests
  were served from the count cache. The fix round's run added the reviser requests with 68 more free counts,

- `uv run python scripts/spikes/v19_token_bound.py --analyse`, which ended with exit 0.
