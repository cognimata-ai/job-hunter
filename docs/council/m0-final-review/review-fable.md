## Strengths

- **Singleton and fencing are correct and defended at every layer.** One autocommit lock session (`lock.py`) carries lock, heartbeat and the §3.3.1 statement verbatim; the watchdog exits with `os._exit(70)` and resolves the stop-vs-fail race under a lock (`watchdog.py:59-74`). The epoch claim proves *in its own transaction* that the claimant's backend holds the lock before writing anything (`epoch.py:117-121`, ruling T8-h), runs under `SET LOCAL lock_timeout` so a frozen holder's row lock ends the claim with 55P03 instead of a hang (`epoch.py:116`, `main.py:161-169`), and the runs sweep deliberately does not skip locked rows (`runs.py:177-182`). `tcp_user_timeout` on the lock session (T8-g) closes the silent-TCP-loss hole that keepalives alone leave.
- **One ownership-loss protocol.** `executions.run_owned` is the only way runs and operations execute; a cancel that the work swallowed is still `lost` (`task.cancelling() > 0`, `executions.py:142-146`), `FencedOut` is `lost`, and no owner write follows a loss. `transition()` builds its statement from registry identifiers only, clears ownership columns in the same `UPDATE`, and the DB trigger plus migration 0003 (app role cannot edit the matrix) give real defence in depth.
- **Auth is carefully phased.** Read-only lockout pre-check, one Argon2 verification whatever the outcome (dummy verify for unknown users, TOTP decrypted before the password so a key mismatch is no oracle), decision under the xact advisory lock first, success re-checked against the user row `FOR UPDATE`, TOTP replay refused by `totp_last_step`, presented session rotated, and the transaction commits before any `Problem` is raised (`routes/auth.py:97-146, 232-280`). `__Host-` cookie flags, HMAC-only storage, Origin + `X-JH-Request` enforced at the outermost ASGI layer, problem+json and edge headers on every response including the last-resort 500.
- **Idempotency is byte-exact and race-safe**: claim-in-transaction with a bounded lock wait → 409, replay from the stored JSONB, handler failure leaves no row, `active_config FOR SHARE` taken before the key (P18), all proven by lock-observing tests (`test_runs_api.py:91-139, 189-269`).
- **Least privilege in the database**: `REVOKE ALL ON DATABASE … FROM PUBLIC`, restore role without CONNECT, `REVOKE CREATE ON SCHEMA public`, migrator-owned objects with default privileges, PostgreSQL logging settings exactly per §16.8, migrate serialised on a polling advisory lock that cannot deadlock `CREATE INDEX CONCURRENTLY`.
- **Delivery**: digest-pinned images, SHA-pinned actions, `uv sync --locked`, non-root 10001 with group 10010, read-only rootfs, `cap_drop: [ALL]`, api on two `internal: true` networks only, a fixed trusted forwarder whose `X-Forwarded-For` is overwritten by Caddy, secrets created 0440 behind an atomic `ln`.
- **Tests prove what they claim.** Crash tests drive real processes, age heartbeats by SQL rather than by waiting, and use readiness acknowledgements (`fault_point_reached`, `holder_ready`) and `pg_stat_activity`/`pg_locks` observation instead of sleeps. Review Focus 1–5 are each pinned by a non-vacuous test (`test_api_recovers_after_db_restart`, `test_watchdog_exits_on_db_restart`, `test_c17_zombie_worker_writes_nothing`, `test_long_downtime_records_every_slot_once`, `test_username_match_*`, the two blocked-behind tests, `test_tick_with_clock_behind_cursor_is_noop`).

## Issues

### Critical (Must Fix)

None found. I walked split-brain (two starters on an empty DB, DB restart, frozen holder with and without a row lock, lock session termination), zombie writes after takeover, claim-token ABA, cancellation during finalize, and the login/idempotency races; every path ends with a fenced 0-row write or a bounded exit.

### Important (Should Fix)

1. **Operations takeover sweep skips locked rows, so a zombie's operation survives the takeover with a valid claim.** `worker/operations.py:142-145` (`_OLDER_EPOCH … FOR UPDATE SKIP LOCKED`, used by `sweep_older_epoch_operations`, lines 367-373). This contradicts `epoch.py:18-22` ("the sweeps wait for the row locks of older owners, they never skip a row"), ruling T12-g, and spec §3.3.1 ("old owners are invalidated atomically at takeover, without waiting for their heartbeats to go stale"); the runs sweep (`runs.py:177-182`) does it right.
   *Scenario:* worker A (epoch N) is mid-`lock_operation_owner` (`FOR SHARE`, `operations.py:134`) or `requeue_operation` (`_OWNED_ATTEMPTS … FOR UPDATE`, line 136) when it freezes; its transaction becomes idle-in-transaction (killed only after 60 s). B takes over at ≥60 s staleness, its sweep runs while that lock is still held, skips the row, and commits epoch N+1 with the operation still `running`, `claim_id` = A's, `worker_epoch` = N. A resumes: for up to one watchdog period its `heartbeat_operation` (`id, claim_id, status='running'`) still updates 1 row and its owner writes still pass `lock_operation_owner`. In M1+ that is a verified-predicate dispatch by a superseded owner, the exact double-dispatch C28/C35 exist to prevent; in M0 the row is simply orphaned until the 3-minute stale reclaim, which is what the spec says takeover avoids.
   *Fix:* drop `SKIP LOCKED` from `_OLDER_EPOCH`; the claim's `lock_timeout` (T13-b) already bounds the wait exactly as for runs. Keep `SKIP LOCKED` on `_STALE` (documented, correct). Add a test mirroring `test_a_row_lock_held_past_the_lock_timeout_fails_the_claim…` for a locked operation row (55P03, nothing committed).

2. **Unbounded concurrent Argon2 work on the login path can exhaust the api container's memory.** `api/routes/auth.py:189, 198, 206` and `auth/users.py:106, 141` run `check_password`/`dummy_verify`/`hash_password` (`memory_cost=65536` KiB = 64 MiB each, `passwords.py:19`) via `asyncio.to_thread`, i.e. the default executor of `min(32, cpu+4)` threads, with no semaphore. Login is unauthenticated, `dummy_verify` makes unknown usernames cost the same, and the lockout pre-check only helps *after* five failures per address have been recorded, which happens after the hash.
   *Scenario:* on an 8-vCPU host, 12 parallel `POST /api/auth/login` from three addresses (four each, under the per-IP threshold) run 12 × 64 MiB ≈ 768 MiB of Argon2 arenas on top of the process baseline inside `mem_limit: 1g` (`deploy/compose.dev.yaml:102`); the kernel OOM-kills the api, every in-flight request fails, Compose restarts it, and the attacker repeats before any lockout exists. No data loss, but a trivially repeatable unauthenticated crash of the internet-facing service.
   *Fix:* a module-level `asyncio.Semaphore(2)` (or a dedicated two-worker `ThreadPoolExecutor`) around every Argon2 call in the api role; optionally answer 429/503 when more than a few requests are queued behind it. A unit test that `N` concurrent logins never run more than the bound in parallel (count entries into a patched `check_password`).

### Minor (Nice to Have)

3. `tests/crash/test_worker_process.py:65-101` (C17): the test proves the end state (run `succeeded`/attempt 2, threads confined, replacement holds the lock, zombie exits 70) but never asserts the zombie *attempted* a domain write and was refused. If the watchdog's residual wait fires before the graph's finalize, the test passes without exercising the fence. After `SIGCONT`, also `a.wait_event("run_fenced", 20, write="finalize")` (or `execution_lost`) and assert `runs.finished_at` unchanged.
4. Shutdown budget exceeds the stop grace. `shutdown.py:22-24, 59` waits up to 110 s after cancelling the loops; `main.py:233-251` then runs `cancel_all` (≤30 s) and `watchdog.stop` (≤15 s) before closing the lock session, against `stop_grace_period: 120s` (`compose.dev.yaml:108`). A busy worker at shutdown can be SIGKILLed mid-teardown (exit 137, not 0). Derive every wait from one deadline (e.g. `GRACE_S` 90 and a teardown bound of the remainder).
5. Stale cutoffs mix clocks: `operations.py:361, 381` and `runs.py:461, 487` compare DB-written `heartbeat_at` (`now()`) against the worker's `utcnow()`, while readiness deliberately uses the database clock for the same comparison (T14-f, `health.py:67-68`). Harmless on one host; either compute `now() - interval` in SQL or document the single-host assumption next to `OPERATION_STALE`/`RUN_STALE`.
6. `cli_user.py:181-185` verifies the enrolment code but `users.enable_totp` (`users.py:181-185`) does not record its step, so that same code is accepted by the first login within its window. Store `matched_step` in `enable_totp`.
7. `api/deps.py:82-87` consults the rate limiter only after the session validation transaction, so a session over 600/min still costs a DB round trip (and possibly a slide write) per refused request. Key the limiter by `token_hmac` computed before the query and check it first.
8. `auth/throttle.py:76-80` casefolds but does not strip the username, whereas `users.normalize_username` strips, so `" ada"` and `"ada"` produce different `login_attempts.username_hmac`. Normalise with `normalize_username` first.
9. `worker/tick.py:244-251` repeats `runs._defer_attempt` (`runs.py:215-224`), including the `run:{id}:{attempt}` queueing-lock string, against P16; move `_defer_attempt` to `tick.py` (or `tasks.py`) and call it from both.

## Plan/spec issues

- **The plan's Deviations section is not yet complete.** `docs/superpowers/plans/2026-10-16-m0-foundation.md:3367-3414` still lists only the pre-execution deviations; the ledger promised T4-h (REVOKE … FROM PUBLIC), T7-h/T16-a (migrations 0003/0004, `users.totp_last_step`), T8-g (`tcp_user_timeout`), T18-h/T18-i (compose corrections, required public origin), T19 (TypeScript 5.9.3, `/readyz` body) and T20 (gitleaks container, `--no-install-project`) "at T21", and `final-known-items.md` confirms they are still "to be recorded". Roadmap gate 6 requires them recorded (and user-approved where behaviour changes) before "complete"; the roadmap cell already says complete (`roadmap.md:61`).
- **Ruling T12-h** (`progress.md:227`): `schedule.stale_data` (critical) is raised every two intervals while `schedule_state.enabled = false`. The spec is silent, but a reasonable operator who paused the schedule does not expect a critical page for the pause; the M5 alert catalogue (or M2 settings, which introduce the toggle to users) should exempt or downgrade the disabled case. Flagging now so it is not forgotten.
- **Spec §3.3.1 assumes a replacement can exist while the holder is frozen**; with `deploy: replicas: 1` and `restart: unless-stopped` a worker that is `docker pause`d or stalled in a swap storm is never replaced automatically, so collection stops until the dead-man switch (M5) pages. Not a defect of M0, but the runbook (M5) should say that a frozen worker is restarted by hand, and that the takeover protocol then does the rest.
- **Ruling T9-d** (superseded stalled job is marked `failed`): correct for `tick`; for `run_collect` the queueing lock carries the attempt, so no successor exists and the branch cannot fire; the docstring of `release_stalled_jobs` should say which task names may legitimately be superseded, so M1–M3 tasks that add queueing locks do not inherit a silent `failed`.
- Every other ruling in the ledger I checked (P13–P18, T3-*, T4-h, T6-h, T8-h, T10-f/g, T12-d/e, T13-b/f, T14-f, T16-a/c/g, T17-g, T18-i, T20-a/b) strengthens safety or is spec-conformant; none contradicts the spec.

## Assessment

**Verdict:** APPROVE WITH CHANGES

**Reasoning:** The singleton, fencing, auth and idempotency cores are correct, spec-conformant and proven by non-vacuous process-level tests; the two Important items (the operations sweep's `SKIP LOCKED`, which breaks atomic invalidation at takeover for exactly the owner class M1+ will dispatch paid work from, and the unbounded Argon2 concurrency on the unauthenticated login path) are small, local fixes that should land with the deviations bookkeeping before M0 is called complete.
