# Job Hunter: Architecture Proposal (Claude Opus 5.5, council round 1)

Inputs: brief v1 (2026-10-16), `research/sources.md` and `research/tech/tech.md`. Version pins come from those registry snapshots. "UNVERIFIED" marks claims the research does not ground.

## 0. Shape

The system is a Python modular monolith with two entry points:
- **api**: FastAPI, which also serves the SPA.
- **worker**: procrastinate plus LangGraph, used as a library.

Storage is a single **Postgres 17 + pgvector 0.8.7**. It holds the domain data, the queue, checkpoints, the quota ledger and the LLM spend ledger.

An **embedder** container runs arctic-embed-l-v2.0 as int8 ONNX. There is **no Redis**.

All of the following is **deterministic**: fetching, quota, normalisation, dedup, filters, embeddings, aggregation and state transitions. Claude has five bounded jobs:
- CV → profile
- query-plan proposal
- job-facts extraction
- fit scoring
- a conditional critic, which forms an evaluator–optimizer loop with the scorer

Three rules hold throughout:
- The final number is **never** generated by the LLM. It is aggregated from anchored sub-scores whose evidence has been validated.
- Every ad has exactly one explicit pipeline state.
- Every paid request is reserved in a ledger **before** it is sent.

## 2. Decisions

### D1 Language and frameworks
- **Decision.** Python 3.13 with exact pins:
  - `langgraph==1.2.15`, `langgraph-checkpoint-postgres==3.2.0`, `langchain-core==1.6.11`, `langchain-anthropic==1.7.6`, `anthropic==1.15.0`
  - `fastapi==0.143.2`, `pydantic==2.14.1`, `sqlalchemy==2.1.4`, `alembic==1.20.0`
  - `psycopg==3.3.6` + `psycopg-pool==3.3.3` (one driver for ORM, queue and checkpointer), `procrastinate==3.10.0`
  - `httpx`, `pypdf==6.20.1`, `pdfplumber==0.11.10`, `python-docx==1.2.0`, `nh3`, `argon2-cffi`

  A single `LLMGateway` module is the only place that constructs `ChatAnthropic`. It always sets:
  - `base_url="https://api.anthropic.com"` and `api_key` from `JOBHUNTER_ANTHROPIC_API_KEY`
  - explicit `max_tokens`, `timeout=120` and `max_retries=2`
  - `with_structured_output(S, method="json_schema", include_raw=True)` for structured output
  - per-node `effort`, omitted for Haiku

  It never sends `temperature`, a prefill or a forced `tool_choice`.
- **Rationale.** Python has the forced-tool guard, the 5.5 model profiles, `TracePolicy` and a current SDK. JS `@langchain/anthropic` pins SDK 0.122.x and its default `withStructuredOutput` returns 400 on Opus/Sonnet/Fable (tech §B3). The gateway puts every known pitfall behind one tested choke point: `ANTHROPIC_BASE_URL` hijack, the 128k default `max_tokens`, no default timeout, and forced-tool defaults.
- **Rejected.**
  - TypeScript LangGraph.
  - Django.
  - `create_agent`/ReAct loops: unbounded and not reproducible.
- **Risks.** Release churn: mitigated by exact pins and upgrade PRs gated on the eval set (D14). The batch path uses the raw SDK, so a payload-equality test keeps it aligned with the online path.

### D2 Topology, scheduling, run guarantees
- **Decision.** Containers:
  - `caddy`
  - `api`
  - `worker`: 1 replica with two lanes, `pipeline` and `aux`, at concurrency 2
  - `embedder`
  - `postgres`
  - `backup`
  - a one-shot `migrate`

  Procrastinate is both the queue and the scheduler.
  - **Embedder.** A separate container runs onnxruntime plus tokenizers with arctic-embed-l-v2.0 int8, exposed as `POST /embed` on the internal network.
    - Measured: 2.18 docs/s at 1,024 tokens, 2.6 GB RSS.
    - The model is Apache-2.0 with an 8k context, and gave the best cross-lingual DE/EN margin.
    - Queries are prefixed with `query: `.
    - It is a separate process because CPU-bound inference would block the worker's event loop, and LangGraph timeouts are cooperative (tech §A3).
    - TEI was rejected because its CPU throughput is UNVERIFIED.
  - **Schedule.** A static `@app.periodic(cron="*/5 * * * *") tick` works out slots as `anchor + k·interval` (Europe/Berlin) from the active settings. For each due slot it inserts `runs(scheduled_slot)` with `ON CONFLICT DO NOTHING` and defers it with `queueing_lock="pipeline"`.
  - **No overlap.** Three guards prevent it:
    - procrastinate `lock="pipeline"`
    - a partial unique index allowing one active run per lane
    - an advisory lock

    A slot that falls during an active run is recorded as `skipped_overlap`.
  - **Missed slots** are coalesced. After downtime, only the latest missed slot runs, as `catch_up`. The older ones are recorded as `missed`.
  - **Run now.** `POST /api/runs {include_paid:false}` returns 202, or 409 if a run is active. Paid sources must be opted into for each manual run.
  - **Shutdown and resume.**
    - `stop_grace_period: 120s`.
    - Each run writes a heartbeat every 30 s.
    - `recover_stale_runs` re-defers any run with no heartbeat for 3 minutes, via `ainvoke(None, thread_id)`. That re-runs only the unfinished tasks (tech §A3).
    - After 3 failed resumes, the run is marked `failed` and an alert fires.
- **Rationale.** The database enforces one run per slot, and the queue is transactional with the domain data. Procrastinate's cron is static, so the tick plus our own slot logic is what makes the schedule configurable from the UI.
- **Rejected.**
  - APScheduler 3: single process only, no queue.
  - APScheduler 4: still alpha.
  - Celery or arq: both need Redis.
  - Temporal: too heavy for one box.
  - PgQueuer: its missed-run semantics are UNVERIFIED.
- **Risks.** How procrastinate handles stalled jobs is from memory, not verified. The heartbeat recovery covers that gap.

### D3 Database, vector store, cache
- **Decision.** `pgvector/pgvector:0.8.7-pg17`, pinned by digest, with:
  - `halfvec(1024)` + HNSW cosine index, `hnsw.iterative_scan=relaxed_order`
  - `pg_trgm`
  - `unaccent` behind an IMMUTABLE wrapper, plus a `german_unaccent` FTS config

  Caching is DB-native:
  - `ad_facts` keyed by content hash
  - scores keyed by scoring-config hash
  - raw payloads archived for 30 days, which also lets a crashed paid fetch be **replayed instead of re-billed**

  No LangGraph `CachePolicy`: it only offers memory or Redis backends and is not auditable.
- **Rationale.** At 10⁴–10⁵ ads the data is tiny. One store makes ledger, state and queue transactional together, which is the core anti-silent-failure property.
- **Rejected.**
  - Qdrant or another separate vector DB: a second consistency domain.
  - Ubuntu pgvector 0.6.0: no `halfvec`, no iterative scan.
  - Redis: nothing requires it.
- **Risks.** Filtered HNSW can under-return. Iterative scan addresses this, and exact scans are affordable at this size.

### D4 Source adapters, query planning, quota
- **Decision.** Common interface:
  ```python
  class SourceAdapter(Protocol):
      id: SourceId; paid: bool; limits: RateLimits
      def build_requests(task: SourceTask) -> list[PlannedRequest]
      async def fetch(req, ledger) -> FetchResult      # raw, cursor, billed, quota observation
      def parse(raw) -> Iterable[RawItem | ContractViolation]   # pydantic raw contract
      def normalize(item, fetched_at) -> NormalizedAd           # pure function
  ```
  - **Query plan.** At profile confirmation an LLM proposes 4–10 role queries in DE and EN, for example "Backend Entwickler Python" or "Python Developer". The user approves them. Runtime planning is deterministic: paid tasks are `(query × location)` pairs ranked by `weight × staleness × (0.5 + yield_ema)`, and free sources run every run.
  - **JSearch (primary).**
    - Calls `/search-v2` with `country=de`, the location inside the query text, and `num_pages=1`.
    - `date_posted` is the smallest window that is at least the gap since the last success plus 24 h, because dates are only precise to the day.
    - Takes page 2 only if page 1 was ≥70% new.
    - Keys on `job_uid`, never `job_id`.
    - Persists `x-ratelimit-requests-remaining/-reset`.
  - **SerpApi (fallback only).**
    - Calls `q="<role> <city>"` with `gl=de`, `hl=de` and no `location` parameter.
    - Reads the free `account.json` before its first use in a run.
    - Keys on `htidocid` decoded from `job_id`.
    - Empty pages count as billed.
    - It only runs paid tasks that JSearch did not serve in this run, and only when JSearch is at its reserve, has returned 429, has its breaker open (2 consecutive transient failures), returns 401/403 (critical alert), or has broken its contract. It is never used for extra volume.
  - **Adzuna.**
    - Uses `results_per_page=50`, `what`, `where`, `distance`, `max_days_old` and `sort_by=date`.
    - The ledger enforces all four windows (25/min, 250/day, 1000/week, 2500/month).
    - Items are marked `description_is_partial`.
    - `redirect_url` is used only as an outbound link: it is never a key and never logged.
    - Results carry an attribution badge.
  - **Arbeitnow.** Follows `links.next` until reaching the high-water mark minus 2 h, up to 10 pages. Hitting the page cap first raises `coverage_truncated`. Location filtering is done locally.
  - **ATS watchlist.**
    - A deterministic detector turns a careers URL into a board. It probes Greenhouse, Lever (global and then `api.eu`), Ashby, Personio XML, Recruitee and SmartRecruiters, and the user confirms the result.
    - The full listing is fetched every run.
    - SmartRecruiters detail calls are made only for new postings, at most 4 concurrently.
    - Workable is off by default.
  - **Retries.**
    - Free GETs: 3 attempts with jittered backoff, honouring `Retry-After`.
    - Paid calls: at most 1 retry, and each attempt makes its own reservation.
    - Timeouts: 5 s connect, 30 s read.
    - Per-host token buckets; the JSearch rate is 1 rps (UNVERIFIED limit).
  - **Breaker.** Persisted in `source_health`. It opens after 3 failed runs, then sends a one-request half-open probe.
  - **Planner.** See §6.
- **Rationale.** Free sources carry the volume. The two paid APIs are windows onto the same Google index, so they buy breadth of discovery, not volume.
- **Rejected.**
  - LLM-generated queries on every run: spend becomes non-deterministic.
  - SerpApi as co-primary: contradicts the user's decision.
  - `uds` date tokens: their reuse is UNVERIFIED.
- **Risks.**
  - "Location in the query" rests on a single observation; zero-yield detection (§7 #3) guards it.
  - `htidocid` stability across days is UNVERIFIED; the second-tier keys cover it.

### D5 Normalised schema and deduplication
- **Decision.** `NormalizedAd` fields:
  - `source`, `native_id`, `title_raw/title_norm`, `company_raw/company_key`
  - `locations[{city, region, country, lat, lon}]`, resolved through an **offline GeoNames DE gazetteer**
  - `work_mode` (+ provenance), `employment_types[]`
  - `posted_at` + `posted_precision ∈ {exact, day, relative, ingest}`, `first_seen_at`
  - `description_text`, `description_html` (nh3-sanitised), `description_is_partial`, `description_quality ∈ {ok, short, garbage}`
  - `language`, `salary{…, is_predicted}`, `apply_url`, `canonical_url`, `publisher_ids[]`, `htidocid`

  Normalisation:
  - Titles: NFKC; strip U+00AD; strip gender tags (`(m/w/d)`, `(w/m/d)`, `(all genders)`, `(*)`, `(f/m/x)`, `(w_m_d)`); map `Sr.` to senior.
  - `company_key`: unaccented and lowercased, with legal forms stripped (`GmbH & Co. KG`, `GmbH`, `AG`, `SE`, `UG`, `PLC`).
  - URLs: canonicalised, with `utm_*`, `gclid` and `fbclid` stripped.
  - Relative dates (`vor N Tagen`, `Gestern`): resolved against the response `Date` header in Europe/Berlin.
  - Quality gate: under 200 chars is `short`; literal `null` lines or a high share of non-letters is `garbage`.

  **Dedup ladder:**
  1. **Upsert.** `UNIQUE(source, native_id)`. A new `content_hash` creates a new version.
  2. **Exact keys.** These live in `ad_keys(key_type, key_value) PK`:
     - `htidocid`
     - `pub:<domain>:<id>`, taken **only from the primary link** (JSearch `job_apply_link`, SerpApi `via`). Other `apply_options` were contaminated in 2 of 10 results.
     - `adzuna:<id>`
     - `arbeitnow:<id>`
     - `ba_refnr` (from it-jobs.de links)
     - `ats:<type>:<board>:<id>`

     If one key hits two clusters, they merge into the lower id, unless a `dedup_override` exists.
  3. **Guarded fuzzy match.**
     - Candidates must share `company_key`, have a compatible location (same city or remote), and fall within 45 days.
     - Their sets of role-level tokens must be **identical** ({senior, junior, lead, principal, werkstudent, praktikum, intern}). Trigrams ignore word order, so this guard is needed.
     - Title trigram similarity must be ≥ 0.85.
     - 5-word-shingle text match: full vs full needs Jaccard ≥ 0.6 or containment ≥ 0.8. Partial vs full needs snippet containment ≥ 0.7, since an Adzuna snippet is the start of the description.
     - Grey zone (title ≥ 0.75): **no merge**. Write `dedup_candidates(needs_review)` instead, which the UI shows as "possible duplicate".
  4. **Same-source rule.** Distinct ids from one source never auto-merge. The exception is Adzuna re-ingests: identical title, company and city, with containment ≥ 0.9.

  **Merge policy.**
  - A cluster keeps every item it absorbs.
  - Fields come from a fixed precedence and are recorded in `field_provenance`:
    - description: the longest non-partial one, ranked ATS > Arbeitnow > JSearch > SerpApi > Adzuna
    - posted date: the earliest at the best precision
    - apply URL: the employer's own link over a publisher's
  - A full-text twin joining a partial cluster creates a new version, which triggers a re-score.
  - A new id that matches a `closed` cluster is linked as `reposted_from_id`.

  **Expiry.** ATS boards are authoritative: an ad is `closed` after being absent from 2 consecutive *successful* listings. For aggregators, an ad goes `stale` 30 days after it was last seen. A failed fetch never ages anything.
- **Rationale.** Certain keys come first, then guarded, explainable fuzzy matching with an explicit "don't know" outcome. No embedding or LLM dependency, so a reviewer can audit every decision.
- **Rejected.**
  - Embedding-cosine dedup: its thresholds are model-specific.
  - LLM dedup.
  - A union over all `apply_options`: proven false merges.
- **Risks.** Agency reposts with different company names remain as visible duplicates. Thresholds are calibrated on the 9 known cross-source pairs plus negatives, then rechecked against unmerges.

### D6 Deterministic vs agentic; graphs
- **Decision.** The deterministic/LLM split follows §0. There are four graphs (§3):
  - `collect_graph`
  - `score_graph`, with the `score_ad` subgraph
  - `profile_graph`

  Fan-out uses `Send`: per source task at `max_concurrency=6`, and per ad at 4.

  Checkpoints go to `AsyncPostgresSaver` with `durability="sync"`. State holds **IDs and counters only**, so checkpoints contain no PII and are purged after 14 days.

  Idempotency works in two places. A score that already exists for a (version, config) pair is skipped. A billed paid fetch with an archived payload is **replayed** rather than re-requested, keyed by `request_key=sha1(run_id, task_key, page)`.

  Quarantine has two forms: items in `rejected_contract`, and ads in `quarantined`. Both are listed under Settings › System › "Needs attention", with a retry button.
- **Rationale.** Bounded workflows that use the required patterns explicitly: fan-out, evaluator–optimizer, and typed per-node error handlers.
- **Rejected.**
  - A free-form tool agent: cost is unbounded.
  - One mega-graph: a CV re-score would drag collection along with it.
- **Risks.** The checkpoint schema can change in an upgrade. Threads are short-lived, so they can be dropped before upgrading.

### D7 Scoring design
- **Decision.**
  1. **Hard filters.** These are deterministic and act only on *positive evidence*. An unknown value passes. Filters:
     - location outside Germany
     - beyond the radius and not remote
     - older than the maximum age
     - excluded company or keyword
     - unaccepted language
     - structured employment-type mismatch

     They are re-evaluated whenever the scope changes.
  2. **Embedding pre-filter.**
     - Query vectors: one profile summary plus one per role query. `sim` is the maximum over them.
     - An ad passes if `sim ≥ τ` **or** it is in the run's top-N.
     - τ is the larger of two values: a floor from 20 known-irrelevant anchor ads (cosine bands vary by model, tech §C3), and the percentile that fits the LLM budget.
     - **Recall audit:** 5% of the ads below τ (at least 2 per run) are scored anyway. If one of them reaches `min_score`, τ is lowered and a warning fires.
     - Ads below τ go to `prefiltered_out`. They stay browsable and can be sent for scoring with "Score this".
  3. **Facts extraction.** This step is independent of the CV. It extracts:
     - work mode
     - required languages with CEFR level
     - seniority and years
     - must-haves and nice-to-haves
     - salary
     - `not_a_job_ad`

     A deterministic gate then applies the user's *hard* constraints.
  4. **Rubric, aggregation, evaluator–optimizer.** See §5.
  5. **Versioning.** `scoring_config_hash = sha256(profile_version, rubric_version, prompt_hash, schema_version, {node: (model, effort)})`, unique per ad version. Ranking uses scores from the current config. An older score shows a **stale-score** badge.
  6. **Re-score triggers.**
     - A newly confirmed profile: re-embed and re-prefilter first, then re-score in order of the previous score.
     - A rubric or model change.
     - A new ad version, or a full-text twin merging into a partial cluster.

     A scope change only recomputes filters and the deterministic criteria. The UI shows a cost estimate before any bulk job.
  7. **Cost controls.**
     - A cached system prefix of about 5k tokens (rubric, anchors, 2 examples, profile), sized above the cache minimum and checked via `cache_read_input_tokens`.
     - Facts are extracted once per content version.
     - Model and effort are set per node.
     - A monthly $ cap is enforced by `llm_ledger`. When it is hit, ads go to `budget_deferred`.
     - At most 150 ads are scored per run.
     - The **Batches API is used only for bulk re-scores of 200 or more ads**: the first pass runs in a batch, the critic online. Incremental runs stay online to keep results fresh.
  8. **Calibration.**
     - a golden set
     - 2 canaries per day, alerting if one moves by more than 8 points
     - test-retest SD ≤ 5
- **Rationale.** Arithmetic and gates stay deterministic. The LLM judges only against anchors and has to quote its evidence. Keeping extraction separate makes CV changes cheap.
- **Rejected.**
  - An overall score emitted by the LLM.
  - Fixed cosine thresholds.
  - A critic on every ad.
  - Batching incremental runs: results could be up to 24 h stale.
- **Risks.**
  - Prompt injection in ads. Mitigated by delimiters, the detector (V6), and grounding.
  - Variance in thinking tokens, which affects cost (§8).

### D8 CV ingestion
- **Decision.**
  - **Upload.** PDF or DOCX up to 10 MB, checked by magic bytes and parsed in the aux lane.
  - **Text extraction.**
    - PDF: pypdf, falling back to pdfplumber.
    - DOCX: python-docx.
    - Scanned files with under 300 characters of text are sent to Claude as a native PDF `document` block.
  - **Contact stripping.** A regex pass removes emails, phone numbers, addresses and date of birth before any LLM or embedding call.
  - **`extract_profile`.** Opus at high effort produces a `CandidateProfile`:
    - target_roles
    - seniority
    - years
    - `experience[]`
    - `skills[{name, level, years, evidence}]`
    - `languages[{code, cefr}]`
    - domains
    - home_city

    It has no name or contact fields. A deterministic validator checks it, and then `propose_queries` runs.
  - **Confirmation.** The user edits the form and clicks **Confirm**. That creates an immutable `profile_versions` row, which triggers re-embedding and a re-score estimate. A draft never activates itself.
- **Rationale.** The scorer sees only what the user confirmed. That keeps scores traceable and the personal data minimal.
- **Rejected.**
  - PyMuPDF: AGPL licence.
  - docling and unstructured: they pull torch into the image.
  - Scoring against the raw CV.
- **Risks.** Multi-column PDFs can come out in the wrong order. The user review catches this.

### D9 Settings model
- **Decision.** Settings are immutable, Pydantic-validated `settings_versions` rows with an active pointer. Each run snapshots the version it started with.

| Group | Fields (defaults) |
|---|---|
| Schedule | enabled (true); interval_hours ∈ {1,2,3,4,6,8,12,24,48,168} (6); anchor 06:00 Europe/Berlin |
| Scope | locations[{city, radius_km 30}] (CV home city); remote_de_ok (true); work_modes with preference weights (all three); employment_types {FULLTIME}; seniority_range (profile ±1); ad_languages {de,en}; required-language hard toggle; max_ad_age_days 30; industries include/exclude; excluded_companies; excluded_title_keywords (Praktikum, Werkstudent, Ausbildung, Minijob if ≥ mid); exclude_temp_agencies (false); min_salary_eur (null); min_score_display 50 |
| Sources | enable flags; JSearch/SerpApi monthly_limit 200/250, reserve 10%; Adzuna windows; per-run caps; watchlist |
| LLM | per-node {model, effort}; monthly_cap_usd; max_ads_per_run 150; batch_bulk_rescore (true); explanation_language (en/de) |
| Retention | expired ads 90 d; raw payloads 30 d; LLM transcripts 90 d |

Validation rules:
- At least one location, or remote enabled.
- Radius 0–200 km.
- **Paid-budget projection:** the §6 functions run against a simulated schedule. If the configuration would overrun, the UI shows how often each paid query would refresh and how many tasks rotate, and saving requires an explicit acknowledgement.
- **LLM projection:** monthly $ is estimated from the trailing-7-day ad volume × per-node unit cost.

- **Rationale.** Every run and every score can be traced to an exact settings snapshot.
- **Rejected.** Mutable settings: there is no audit trail, and edits can leak into a run that is already in progress.
- **Risks.** Too many knobs. Advanced fields are collapsed, and each default is documented in the UI.

### D10 Jobs page
- **Decision.**
  - **Filters**
    - Posted within 24 h, 3 d, 7 d, 14 d or 30 d. This uses `posted_at_effective = min(provider date, first_seen)`, and imprecise dates show "≈".
    - Score and confidence.
    - City plus radius, resolved through the gazetteer.
    - Work mode, text, source and language.
    - Status and lifecycle.
    - Toggles to include unscored, filtered or partial ads.
  - **Sort**: by score, posted date or first seen.
  - **Paging**: keyset over `(sort_value, id)`, 50 per page.
  - **Search**: a weighted generated `tsvector` built with `german_unaccent` or `english` depending on the ad language. It is OR-ed with a trigram `title ILIKE`, because the German stemmer does not split compounds like "Softwareentwickler".
  - **User status**: new, seen, saved, applied or hidden. This is kept separate from the pipeline state.
  - **Detail view**
    - Each field with its provenance.
    - All source links, including the Adzuna attribution.
    - Extracted facts.
    - For each criterion: level, weight, evidence quotes and rationale.
    - Gates, confidence, partial and contested badges, and critic notes.
    - The score version.
    - Actions: "Re-score" and "Not a duplicate".
  - **Freshness strip**: for example "last successful run 2 h ago · JSearch exhausted until 16 Nov".
  - Stale and closed ads are hidden unless they are saved or applied.
- **Rationale.** Postgres FTS plus trigram search is enough at this scale. Keyset paging stays stable while inserts are happening.
- **Rejected.**
  - Offset paging.
  - Meilisearch: a second index that would have to be kept in sync.
- **Risks.** German compound words. The trigram OR covers them; if recall turns out poor, a hunspell dictionary that splits compounds is the next step.

### D11 Frontend, API, auth
- **Decision.**
  - **Frontend.** React 19.3.1 + Vite 8.3.4 SPA with TanStack Query 5.104.3 and TanStack Router 1.170.44, EN/DE i18n, served statically by `api`. TypeScript is pinned to the newest major the toolchain supports; TS 7 support is UNVERIFIED.
  - **API.** REST with an OpenAPI 3.1 spec. The TS client is generated from it, and CI fails on drift.
  - **Auth.**
    - Users: exactly one row (`CHECK id=1`), password hashed with Argon2id.
    - Bootstrap: `docker compose run --rm api jobhunter set-password`, with optional TOTP.
    - Sessions: server-side in Postgres. The cookie is `__Host-jh` (Secure, HttpOnly, SameSite=Strict), with a 12 h idle and 30 d absolute lifetime.
    - CSRF: double-submit token plus an `Origin` check.
    - Login throttling: 5 failures per 15 min per IP; 20 per hour globally triggers a lockout and an alert.
  - **Headers (Caddy).** HSTS, a CSP of `default-src 'self'`, `frame-ancestors 'none'`, and `Referrer-Policy: no-referrer`.
  - **Ad content.** Ad HTML is sanitised with nh3.
- **Rationale.** One origin, one runtime and cookie sessions keep the attack surface small. Every security control is boring and can be tested.
- **Rejected.**
  - Next.js.
  - JWT stored in localStorage.
  - Basic auth.
- **Risks.** A single password on the internet. Mitigated by TOTP, Argon2 and throttling.

### D12 Error handling and fault tolerance
- **Decision.**
  - **Typed errors.** Sources raise `SourceError(kind=transient|auth|quota|contract|bug)`. LLM calls raise `LLMError(kind=rate|server|timeout|invalid_request|refusal|max_tokens|schema|budget)`. Node handlers turn these into typed outcomes, and only `bug` fails a run. A ruff rule bans bare `except`.
  - **Retries.** LLM nodes retry only `NodeTimeoutError`, up to 2 attempts. The SDK owns retries for 429 and 5xx, and a 400 is never retried (tech §A3).
  - **LLM outcomes.**
    - Refusal → `quarantined`.
    - `max_tokens` → one retry at twice the limit.
    - Transient error → `score_failed` with backoff; after 3 failures, `quarantined`.
    - Spending cap reached → `budget_deferred`.
  - **Quota exhausted.** The run continues on free sources only and finishes as `completed_degraded`.
  - **Invariants.** `finalize_*` checks three things:
    - `received = inserted + updated + unchanged + rejected`
    - exactly one outcome per task
    - no ad left in `scoring` without an active run

    A violation marks the run `failed_invariant` and raises a critical alert.
  - **Visibility.** Run reports are shown under Settings › System.
  - **Fallbacks.** The `fallbacks` beta stays **off**, because it can switch models silently.
- **Rationale.** Errors are part of the data model: every failure ends up as a state, a ledger row, or a report count that a reviewer can query.
- **Rejected.**
  - Fail-fast whole runs: one bad source would block all the others.
  - Swallow-and-log: errors would be dropped silently.
- **Risks.** Alert fatigue. Alerts are deduplicated by key.

### D13 Observability
- **Decision.**
  - **Logs.** structlog JSON with IDs (`run_id`, `task_key`, `ad_id`, `llm_call_id`). Never logged: CV or profile text, descriptions, recruiter contacts, Adzuna `redirect_url`, secrets. A redaction processor runs as a backstop.
  - **Metrics.** `/metrics` exposes Prometheus metrics. The primary view is DB-backed (runs, ledgers, `llm_calls`, `field_presence_stats`, alerts) and shown under Settings › System.
  - **LLM trace.** Each `llm_calls` row stores:
    - the request and response bodies, kept 90 days
    - token counts, including cache usage
    - cost and stop reason
    - the model requested and the model served
  - **LangSmith.** Off by default. If it is enabled: inputs and outputs are hidden, the EU endpoint is used where applicable, and a startup assertion confirms no gateway is configured.
  - **Health.** `/healthz` for liveness. `/readyz` checks:
    - DB reachable, Alembic at head
    - embedder up
    - worker heartbeat < 2 min
    - last tick < 10 min
    - full vector coverage
  - **Alerting.**
    - an in-app banner
    - SMTP or ntfy for warn and critical, throttled per key to once every 6 h
    - an external dead-man switch pinged after every scheduled run
- **Rationale.** For a single user, the database tables that record runs and calls are the observability store: they can be queried and are shown in the UI. Only the dead-man switch has to live outside the box.
- **Rejected.** A Prometheus/Grafana/Loki stack: too heavy for one user. It can be bolted onto `/metrics` later.
- **Risks.** `llm_calls` bodies contain ad text. They are retained for 90 days and excluded from logs.

### D14 Testing
- **Decision.**
  - **Unit tests:**
    - normalisers
    - German dates and salary formats
    - `htidocid` decoding
    - URL canonicalisation
    - the dedup decision table
    - the gates
  - **Property tests (hypothesis):** for any sequence of schedules, manual runs, crashes and failures, billed plus reserved never exceeds the limit.

  - **Graph tests** run every route against a stub gateway.
  - **Payload tests** assert:

    - no `tool_choice` and no prefill
    - `max_tokens` and `timeout` are set

  - **LLM eval set:** 60–100 pairs, user-labelled plus adversarial (injection, partial ads, language traps, seniority traps). Pass criteria:

    - gate recall 100%
    - Spearman ≥ 0.6
    - retest SD ≤ 5

    It runs on every rubric, model or dependency change.
  - **E2E:** `playwright-cli` against compose, with a fixture source server and a stub LLM. Flows covered:

  - **CI:** GitHub Actions. A weekly live smoke test calls **free sources only**.
- **Rationale.** The real risks here are integration drift and silent behaviour, so contract, invariant and eval tests matter more than line coverage.
- **Rejected.**
  - Live paid-API calls in CI: they would spend quota.
  - Snapshot-testing raw LLM output.
- **Risks.** A small eval set is noisy, so thresholds are kept conservative and the set grows as the user gives feedback.

### D15 Deployment
- **Decision.**
  - **VPS:** German region, 4 dedicated vCPU, 16 GB RAM, 160 GB NVMe, ideally with AVX-512 VNNI. Run the embedding benchmark at provisioning; if int8 is slow on that CPU, switch to fp16 ONNX.
  - **Memory budget:**

    | Service | RAM |
    |---|---|
    | Postgres | ~4 GB |
    | Embedder | ~3 GB |
    | Worker | 1.5 GB |
    | API | 0.5 GB |

    8 GB total would be too tight.
  - **Compose:**
    - Only Caddy publishes ports.
    - Two networks: `edge` and `internal`.
    - Every service has a healthcheck.
    - A one-shot `migrate` service runs Alembic, the procrastinate schema and `PostgresSaver.setup()`. The other services wait on `service_completed_successfully`.
    - Migrations follow expand/contract.
  - **Images:** pushed to GHCR by digest. Rollback means redeploying the previous digest.
  - **Model packaging:** the embedding model is downloaded at **build time** from a pinned HF revision and sha256-checked. A model change ships as a new image plus a re-embed job.
  - **Backups:** nightly `pg_dump`, encrypted with age, stored offsite. Keep 7 daily, 4 weekly and 3 monthly copies. A restore test runs monthly and raises an alert on failure.
- **Rationale.** One box running Compose matches the user's decision. Everything is pinned, migrations come first, and a backup counts only once a restore has been proven.
- **Rejected.**
  - Kubernetes.
  - Managed Postgres: it adds cost and a data processor, and isn't needed.
  - Downloading models at runtime.
- **Risks.** One VPS is a single point of failure. The dead-man switch makes an outage visible, and recovery is a restore onto a fresh VPS (RTO is hours, which is acceptable).

### D16 Retention and GDPR
- **Decision.**
  - **Data minimisation.** Contact data is stripped before any LLM call, and checkpoints hold IDs only.
  - **Retention periods:**

    | Data | Kept for |
    |---|---|
    | Checkpoints | 14 d |
    | Raw payloads | 30 d |
    | LLM bodies | 90 d |
    | Logs | 14 d |
    | Expired-ad descriptions | 90 d, then a tombstone (keys, hashes, user status) |

    Old profile versions are pruned once nothing references them. The CV original can be deleted after confirmation.
  - **"Delete all my data".** Wipes the CV, profiles, vectors, scores, transcripts and checkpoints. Backups age out within 3 months.
  - **Adzuna termination.** `purge_source('adzuna')` removes Adzuna data if that agreement ends.
  - **Recruiter personal data in ads.** Never logged, and scrubbed from fixtures.
- **Rationale.** Keep the minimum of personal data, keep it for the shortest time, and make deletion one action.
- **Rejected.** Keeping everything forever, and encrypting at the field level: a single-user box with disk encryption and IDs-only state already covers this.
- **Risks.** Backups lag deletion by up to 3 months; the UI says so. Anthropic's retention terms are a decision for the user (Q5).

**collect_graph:** `START → init_run → plan_tasks ⇒ fetch_source (Send ×N) → plan_fallback ⇒ fetch_fallback (Send ×M | skip) → reconcile_quota → dedup_cluster → filter_and_embed → finalize_collect → END`

| Node | Kind | Behaviour | Retry / timeout | On error |
|---|---|---|---|---|
| init_run | det | lock run, freeze settings/profile ids, start heartbeat | – / 30 s | run failed |
| plan_tasks | det | §6 allowances; free tasks + ranked paid tasks | – / 30 s | run failed (bug) |
| fetch_source / fetch_fallback | det I/O | reserve → fetch → archive → parse → normalise → upsert `source_items` | adapter-level (D4); `TimeoutPolicy(run_timeout=600)` | handler → `TaskOutcome(failed, kind)`; never raises |
| plan_fallback | det, conditional | tasks JSearch did not serve → SerpApi if the D4 policy allows | – | – |
| reconcile_quota | det | ledger vs headers/account.json → adjustment + alert | 3× on DB error | warn |
| dedup_cluster | det | D5 ladder, one tx per block, advisory lock on company_key | – / 900 s | run failed; items stay `normalized` |
| filter_and_embed | det + embedder | hard filters → embed new versions (batches of 16) → sim → τ/top-N/audit | `RetryPolicy(3, retry_on=EmbedderUnavailable)` / 1800 s | ads stay `awaiting_embedding`; alert |
| finalize_collect | det | invariants, report, alerts, dead-man ping; defers `run_score` | – | `failed_invariant` |

**score_graph:** `START → select_batch ⇒ score_ad (Send per ad, max_concurrency=4) → finalize_score → END`.
- `select_batch` takes `awaiting_score` ads up to the per-run cap and the remaining LLM budget.
- Order: re-scores by previous score descending, then new ads by `sim` descending. Audit samples are always included.
- Selected ads are marked `scoring` with the run id.

**score_ad subgraph** (compiled, added as a node, inherits the checkpointer):

```
START → load_ctx ─(score exists for config)→ persist(skip)
            └→ extract_facts ─(facts cached: no LLM)→ gate
gate ─(user hard constraint violated)→ persist(gated_out)
     └→ score → validate
validate ─(fatal: schema / missing criteria, repairs<1)→ score   [repair message]
         ─(critic trigger, §5)→ critique
         ─(clean)→ persist(accepted)
critique ─(accept | converged)→ persist(accepted)
         ─(revise, revisions<2)→ score   [critic issues as a new USER turn] → validate
         ─(revise, revisions=2)→ persist(contested)
```

| Node | Kind | Model / effort (config A) | Timeout | Retry |
|---|---|---|---|---|
| load_ctx, gate, validate, persist | det | – | 30 s | persist: 3× on serialization error |
| extract_facts | LLM | Opus 5.5 / low (B, C: Haiku 5.5) | 180 s | `NodeTimeoutError` only, max 2 |
| score | LLM generator | Opus 5.5 / medium | 180 s | same |
| critique | LLM evaluator | Opus 5.5 / high | 240 s | same |

Every LLM node has an `error_handler` that maps `LLMError` to `AdOutcome(score_failed | quarantined | budget_deferred)`.

Revision prompts are rebuilt from the DB in this order:
1. the original messages
2. the prior draft, as an assistant turn
3. the critique, as a **user** turn

The prompt never ends on an assistant turn.

Invocation settings: `recursion_limit=100`, `durability="sync"`.

**profile_graph** (aux lane): `parse_document → strip_contacts → extract_profile (LLM) → validate_profile → propose_queries (LLM) → END`. It writes drafts only; the user confirms.

## 5. Scoring rubric, schema, evaluator–optimizer

| Criterion | By | Weight | Anchors (0 … 4) |
|---|---|---|---|
| role_fit | LLM | 20 | 0 unrelated function · 2 adjacent role · 4 same role family and scope |
| must_have_skills | LLM | 25 | 0 none evidenced · 2 about half · 3 all but one minor/equivalent · 4 all evidenced |
| experience_seniority | LLM | 15 | 0 off by ≥2 levels · 2 one level off · 4 years and level match |
| domain_fit | LLM | 10 | 0 no overlap · 4 same industry/problem domain |
| language_fit | LLM + gate | 10 | 0 required language missing · 2 one CEFR level short · 4 all met |
| nice_to_have | LLM | 5 | share of nice-to-haves evidenced |
| location_workmode | **det** | 10 | distance, work mode, user preference weights; unknown → null |
| compensation | **det** | 5 | only if salary known and `min_salary_eur` set |

**Aggregation (deterministic):**
- `overall = round(100 · Σ_known wᵢ·levelᵢ/4 / Σ_known wᵢ)`. A `null` level means unknown and is excluded from both sums.
- **Gate cap:** if a gate is confirmed (an LLM flag that agrees with the facts or a deterministic check, or a user hard constraint), `overall = min(overall, 25)` and the status is `gated`.
- **Confidence:**
  - low: partial or short description, or known weight < 60
  - medium: 1–2 criteria unknown
  - otherwise high

**Scorer schema** (`output_config.format`; length limits are enforced by the validator):

```json
{"type":"object","additionalProperties":false,
 "required":["criteria","matched_must_haves","missing_must_haves","gate_flags","red_flags","summary"],
 "properties":{
  "criteria":{"type":"array","items":{"type":"object","additionalProperties":false,
    "required":["id","level","evidence_job","evidence_profile","rationale"],
    "properties":{
      "id":{"type":"string","enum":["role_fit","must_have_skills","experience_seniority","domain_fit","language_fit","nice_to_have"]},
      "level":{"anyOf":[{"type":"integer","enum":[0,1,2,3,4]},{"type":"null"}]},
      "evidence_job":{"type":"array","items":{"type":"string"}},
      "evidence_profile":{"type":"array","items":{"type":"string"}},
      "rationale":{"type":"string"}}}},
  "matched_must_haves":{"type":"array","items":{"type":"string"}},
  "missing_must_haves":{"type":"array","items":{"type":"string"}},
  "gate_flags":{"type":"array","items":{"type":"string","enum":["language_requirement_unmet",
     "seniority_far_off","work_mode_incompatible","location_incompatible","employment_type_incompatible","not_a_job_ad"]}},
  "red_flags":{"type":"array","items":{"type":"string"}},
  "summary":{"type":"string"}}}
```

**Critic schema:** `{verdict: accept|revise, issues: [{criterion, problem: ungrounded|anchor_misapplied|too_generous|too_harsh|missed_requirement|injection_influence, suggested_level: 0–4|null, explanation}], notes}`.

**Protocol:**
1. **Generate.**
   - The cached system prefix holds the rubric, the anchors, 2 worked examples and the confirmed profile JSON.
   - The user turn holds `<job_facts>` and `<job_ad>`, marked as untrusted data. The ad is capped at 12k chars (head + tail), and any truncation is recorded.
2. **Validate (deterministic).**
   - **V1** schema parses; otherwise one repair attempt.
   - **V2** all 6 criteria are present, each exactly once.
   - **V3 grounding:** every `evidence_job` quote must fuzzy-match a substring of the ad (whitespace-normalised, ratio ≥ 0.9), and every `evidence_profile` quote must match profile values. An ungrounded quote that supports level ≥ 3 is an issue.
   - **V4 consistency.** Examples:
     - `must_have_skills=4` requires `missing_must_haves=[]`.
     - A fact `requires de≥C1` with profile `de=B1` requires `language_fit≤1` and the gate flag.
   - **V5** length limits.
   - **V6** injection patterns in the ad ("ignore previous", "score this", "as an AI").
3. **The critic runs when any of these hold:**
   - a non-fatal V-issue, or a V6 hit
   - `|overall − min_score_display| ≤ 8` (the decision boundary)
   - `overall ≥ 75` (what the user reads first)
   - a partial description with `overall ≥ 60`
   - a 5% random sample

   Otherwise the draft is accepted, giving about a 35% critic rate.
4. **Optimise.**
   - On `revise`, the scorer gets the critic's issues and returns a full new JSON, which goes through validation again.
   - The draft is **accepted** if the critic accepts, or if two successive drafts are within 3 points with no V-issues (converged).
   - After 2 revisions the result is **contested**: the last draft is persisted with the critic notes and a badge, and confidence drops one level.
5. **Calibrate.**
   - The golden set reports Spearman, MAE, gate recall and test-retest.
   - 2 canary ads are scored daily.
   - Any change of model, effort or rubric creates a new config that must pass the eval set before activation.

## 6. Quota budget algorithm

```python
# Period is anchored to the provider's reset, not the calendar month:
#   JSearch: observed x-ratelimit-requests-reset;  SerpApi: plan_renewal_date (free account.json)
def reserve_floor(qs, now):   # the reserve is released in the final 48 h so it isn't wasted
    return 0 if qs.period_end - now <= timedelta(hours=48) else qs.reserve_units

def used(provider, qs):       # conservative: reserved and unknown count as spent
    return SUM(units) FROM quota_ledger WHERE provider=:provider AND period_start=:qs.period_start
           AND status IN ('reserved','billed','unknown','adjustment')

def run_allowance(provider, now, schedule, manual=False, include_paid=False) -> int:
    if manual and not include_paid: return 0
    with tx(): qs = SELECT … FROM quota_state WHERE provider=:provider FOR UPDATE
        roll_period_if_needed(qs, now)
        remaining = qs.monthly_limit - used(provider, qs)
        if qs.observed_remaining is not None and qs.observed_at >= qs.period_start \
           and qs.observed_remaining < remaining:                    # someone else used the key
            insert_ledger(provider, status='adjustment', units=remaining - qs.observed_remaining)
            alert('quota.unaccounted_usage', provider); remaining = qs.observed_remaining
        spendable = max(0, remaining - reserve_floor(qs, now))
        slots_left = max(1, schedule.slots_between(now, qs.period_end))   # incl. this run
        rate = spendable / slots_left
        units = floor(qs.carry + rate)
        qs.carry = min(qs.carry + rate - units, 3.0)                   # fractional pacing
        if provider == 'serpapi':
            units = min(2 * units, hourly_left(qs, now))               # fallback may borrow one slot
        return min(units, settings.per_run_cap[provider], spendable)

def reserve_unit(provider, run_id, request_key, attempt):            # before EVERY paid call
    with tx(): qs = lock(provider)
        if used(provider, qs) + 1 > qs.monthly_limit - reserve_floor(qs, now): return None
        if provider == 'serpapi' and calls_last_hour(provider) + 1 > min(50, qs.hourly_cap): return None
        if provider == 'adzuna' and any(count(w) + 1 > cap(w) for w in ('1m','1d','7d','30d')): return None
        return INSERT quota_ledger(…, status='reserved', units=1)
               ON CONFLICT (provider, request_key, attempt) DO NOTHING RETURNING id

def settle(ledger_id, resp):
    # JSearch: billed iff remaining-header delta; RapidAPI gateway 404 → not_billed
    # SerpApi: any success incl. EMPTY → billed; error → not_billed;  timeout/crash → unknown (counted)
    UPDATE quota_ledger SET status=…, provider_remaining=…, settled_at=now()
    update quota_state.observed_remaining   # SerpApi: max(local, remote) because this_hour_searches lags

# Planner: tasks by priority; run while run_allowance > 0 and reserve_unit() succeeds;
# page 2 only if page-1 new-ratio ≥ 0.7; unserved tasks → TaskOutcome(skipped_budget), never silent.
```

## 7. Silent-failure register

| # | Failure | Prevention / surfacing |
|---|---|---|
| 1 | Paid quota overrun | Reserve-before-call under a row lock; hard limit minus reserve; crashes leave `reserved`, which counts as spent; property tests |
| 2 | Key used outside the app | Provider remaining below ledger → `adjustment` row + alert |
| 3 | Billed empty SerpApi pages / bad location semantics | Counted as billed; zero-yield streak ≥ 3 → task demoted + warn; never use `location` |
| 4 | Unstable JSearch `job_id` as key | Contract test asserts `job_uid`; `UNIQUE(source, native_id)` |
| 5 | Schema drift: nulls look like data | Pydantic raw contract → `rejected_contract` counts; field presence > 30 points below the 14-day baseline → run degraded + warn |
| 6 | Endpoint removed (like `/search` 404) | Classified as `contract` → breaker + critical alert, never "0 results" |
| 7 | Silent page caps / firehose gaps | Page size read from the response; `count` checks; HWM not reached → `coverage_truncated` |
| 8 | Wrong merge hides a job | Role-level guard; grey zone → no merge; provenance; unmerge + override |
| 9 | `apply_options` contamination | Keys from the primary link only |
| 10 | Stale shown as fresh | `posted_precision`, first/last seen, lifecycle, freshness strip with per-source `last_ok_at`; stale hidden by default |
| 11 | False expiry during outages | Only successful authoritative listings count as misses (×2); TTL measured from last successful sighting |
| 12 | Pre-filter drops good ads | Recall audit + auto-τ; `prefiltered_out` browsable; unknown passes hard filters |
| 13 | Mixed embedding models | Vectors keyed by `model_id`; queries filter on it; readiness needs 100% coverage |
| 14 | Structured output silently via tools, or 400 | Gateway-only `json_schema`; lint bans `bind_tools`/`tool_choice`/methodless `with_structured_output`; payload tests |
| 15 | Refusal / `max_tokens` turned into a 0 score | Explicit states; no score row is written |
| 16 | LangGraph retrying 400s | `retry_on` timeouts only; SDK owns 429/5xx |
| 17 | Hung call (default: no timeout) | `timeout=120` + `TimeoutPolicy` + heartbeat + stuck detector |
| 18 | Wrong-but-plausible scores | Deterministic aggregation, grounding, conditional critic, canaries, golden set, contested badge |
| 19 | Prompt injection in ads | Delimiters, untrusted-data instruction, detector forces critic, V3/V4 |
| 20 | Old-CV score shown as current | Config-hash keyed scores; stale badge; ranking by current config |
| 21 | Prompt cache silently missed | `cache_read_tokens == 0` on more than 3 consecutive scorer calls → warn; prefix sized above the minimum |
| 22 | LLM spend overrun | `llm_ledger` reserve/settle vs cap → `budget_deferred` + banner |
| 23 | Base-URL / LangSmith-gateway hijack | Explicit `base_url`; startup assertion on resolved host and key prefix |
| 24 | PII in logs or traces | Tracing off or hidden; redaction processor; IDs-only state; fixture scrub guard |
| 25 | Scheduler dies silently | External dead-man switch; `/readyz` tick age; overlap/missed recorded as runs |
| 26 | Swallowed fan-out errors | Exactly one `TaskOutcome` per task; count conservation → `failed_invariant` |
| 27 | Partial description scored as full | `is_partial` → low confidence + badge; re-score when a full twin merges |
| 28 | Relative-date mis-parse | Resolved against response `Date` (Europe/Berlin); precision stored; tests on observed strings |
| 29 | Double spend on resume | Score-exists check, `llm_calls.idempotency_key`, paid replay from `raw_payloads` |
| 30 | Settings changed mid-run | Run uses its `settings_version_id` snapshot |
| 31 | Backups silently broken | Monthly automated restore test + alert |
| 32 | XSS via ad HTML | nh3 at ingestion + CSP |
| 33 | Server-side fallback switches model | Off; if enabled, `model_served` is recorded and hashed into the config |

## 8. LLM cost estimate

**Assumptions:**
- **Volume:** about 250 new unique ads per day survive dedup and the hard filters. About **100 per day reach the LLM** (≈40% pass the prefilter, plus audits), so roughly 3,000 per month.
- **Funnel:** 85 pass the facts gate, the critic runs on about 36, and about 12 of those need a revision.
- **Volume is set by the market, not the schedule:** about 25 ads per run on a 6 h schedule, about 100 per run on 24 h.
- **Tokens:** German text is about 4 chars per token, so an average ad is about 1,600 tokens. Thinking is billed as output.
- **Caching:** cache reads cost 0.1× input and cache writes 1.25×. These are Anthropic's standard multipliers and are not stated in the brief, so verify them. Cache writes are negligible (under $0.10 per day).

## 9. Open questions for the user

1. **Models and LLM spend cap.** Which configuration: A (≈$310/month), B (≈$135/month), C (≈$44/month), or a custom mix? What hard monthly cap should apply? I suggest B with a $150 cap; A is Anthropic's guidance default.
