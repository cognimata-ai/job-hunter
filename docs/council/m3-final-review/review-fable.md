#### Important
**I1** — A batch follow-up claimed after an evaluation-policy change is not resumed; the generator is paid again — `backend/src/jobhunter/scoring/targets.py:262–265` (`RESUMABLE_DRAFT_SQL` requires `a.evaluation_policy_id = :policy`), `backend/src/jobhunter/graphs/score/nodes/claim.py:72–77` (`_RESUMED_FROM` under the same predicate, `:policy` = the active policy at claim, `:80–85`), `backend/src/jobhunter/graphs/score/nodes/load_context.py:62–66` (`resumable` bound to the new attempt's policy), `:79–89` (`_CHAIN` drops the `resume_draft_id` attempt unless it is under that policy), `:244` (`_resume` only when `resumable`), `backend/src/jobhunter/scoring/batch_items.py:536–545` (the `followup` move sets `lane='batch_followup'`, `resume_draft_id`). Scenario: a bulk re-score batches 2,000 targets at prepare under policy P1 (`scoring/batches.py` prepare step 1 pins the active policy on the batch attempts); the operator saves an evaluation policy (P2 becomes active) while the batch runs (up to 24 h) or before its follow-ups are admitted; each `followup` item (a billed, structurally valid draft with a trigger, spec L4047) becomes `pending(lane='batch_followup', resume_draft_id)`; its claim pins P2, `RESUMABLE_DRAFT_SQL` is false, `resumed_from_attempt_id` is NULL, `load_context` sets `resumed=False` and routes to `generate`: a new online generator call at online prices, a second draft, and the batch draft is never used. Reproduced by my probe: control `policy_changes=False → outcome=publish(accepted) resumed=True generate_calls=1 drafts=1`; `policy_changes=True → resumed=False generate_calls=2 attempts(policy)=[(3, 4), (4, 6)] drafts=2`. This contradicts spec L3589 ("resumes from DB artifacts: if a previous attempt ... under the same tuple and evaluation policy **(or `resume_draft_id` is set from a batch)** ... so no completed LLM work is repeated") and plan L942 / Deviation 27 (the follow-up "re-validates under its own policy", i.e. the draft is kept and only validation and triggers are re-run under P2). The online crash case is spec-conformant (L3589 conditions an online resume on the same policy), so only the batch exception is missing. The ledger is consistent throughout (both calls are billed once), which keeps this Important rather than Critical; no existing test covers a policy change between the batch attempt and the follow-up claim. Fix: make the predicate `(t.resume_draft_id IS NOT NULL OR EXISTS (... same policy ...))`; in `_CHAIN` keep the policy filter for the attempt chain but always seed the attempt of `t.resume_draft_id` (its round-0 draft is policy-independent; `validate` re-runs the triggers under the new attempt's policy, which is Deviation 27's intent); in `_RESUMED_FROM` name that attempt as `resumed_from_attempt_id` for a `resume_draft_id` target; add the probe's second case as a repository test. `ELIGIBLE_SQL` (`scoring/batches.py:293–302`) already excludes `resume_draft_id IS NOT NULL` targets, so batching is unaffected.

#### Minor
**M1** — `batch.retrieve_failing` has no runbook entry and no operator path — `backend/src/jobhunter/scoring/batch_results.py:116–118`, `:711–739` (`_retrieve`: a failing `retrieve` only logs, and past `expires_at + 1 h` raises the critical alert; `_observe` returns without moving the submission), `backend/src/jobhunter/scoring/batches.py:1091` (`abandon` handles `preparing` only), `:1290` (`release` handles `submit_ambiguous` only), `docs/RUNBOOK.md:74–113` (quarantine and anomaly entries; none for `retrieve_failing`). Scenario: the provider answers a permanent 404 for a recorded `provider_batch_id` (the batch was purged or the id was mis-recorded); the submission stays `submitted` forever, its entries stay `dispatched` (batch entries are never aged, `llm/spend_ledger.py:1939–1972`), the reserved amount stays counted against the month, and prepare refuses every new batch as `in_flight`; the only signal is the critical alert, which the runbook does not explain. This is exactly what spec L4038 and L5628 prescribe (the alert, resolved by the move to `ended`), so it is spec-conformant and far-fetched; the fix is a runbook entry naming the operator's action (today: an SQL move to `submit_ambiguous` followed by the release route), and optionally an API/CLI path for it in M4.

**M2** — `CLAIM_WHERE` is not pinned to `_ADMISSIBLE_WHERE` (parked item 3) — `backend/src/jobhunter/graphs/score/nodes/claim.py:51–55`, `backend/src/jobhunter/scoring/admission.py:329–332`, `tests/support/m3.py:40–70` (the test copy pins the test's own claim). Scenario: a later edit adds a money-gate condition to admission (say a new `not_before`-like column) and forgets the claim; the claim's `FOR UPDATE SKIP LOCKED` re-check would then admit a target the admission predicate excluded. Today both fragments carry the same conditions (`state='pending'`, `not_before`, `charged_attempts < max`, the fence, the cycle predicate), and the claim uses `now()` where admission binds `:now`, a harmless difference within one transaction. Fix: a unit test asserting that every condition of `_ADMISSIBLE_WHERE` appears in `CLAIM_WHERE` (or one shared fragment with the alias parameterised).

**M3** — Stale ratio labels in `docs/spikes/V19.md` (parked item 2) — `docs/spikes/V19.md:40–70`, `:150–200` (0.522 (12/23), 0.521 (99/190), whole 0.482 (2,259/4,691); the reviser framing 473 counted as the generator's).
