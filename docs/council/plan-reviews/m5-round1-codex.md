**Verdict: REJECT**

I read the brief, plan, relevant spec sections, author decisions, research digests and M4 conventions, and checked the proposed contracts against the migrations, transition registry, operation machinery, authentication, deletion helpers and tests. This was a static review: no network, Docker or sub-agents; no `.secrets/`, `.fixtures-raw/` or credentials read; nothing changed.

1. **BLOCKER — The backup Dockerfile cannot build as specified.** P:355; S:6049; `Dockerfile:9` — `COPY --from=${RESTIC_IMAGE}` and `${PGVECTOR_IMAGE}` use unsupported variable interpolation in `--from`, explicitly documented in the existing Dockerfile. — Declare named stages using `FROM ${…} AS …`, then copy from those stage names. Explicitly keep ordinary app builds targeting `runtime`.

2. **MAJOR — Task 21 starts a command that Task 24 has not created.** P:605, P:620, P:674; S:6048; `backend/src/jobhunter/cli.py:13` — Task 21’s full-stack test starts `jobhunter backup scheduler`, but Task 10 produces only `backup init` and `backup ship`; the scheduler arrives in Task 24. The prescribed intermediate stack cannot run correctly. — Move scheduler delivery before Task 21’s full-stack verification, or explicitly stage that verification after Task 24.

3. **MAJOR — The manifest FK breaks existing fence fixtures.** P:117, P:299; S:2802; `tests/support/scoring.py:1241`, `tests/integration/test_is_fenced_profile.py:9` — Existing helpers insert fences with literal manifest IDs 1 and 2 without corresponding manifests. Adding the FK makes these fixtures fail, including suites the plan requires to pass. No task owns their conversion. — Update all fence fixtures in Task 1 to insert a valid manifest and use its returned ID.

4. **MAJOR — Profile purging uses an illegal transition.** P:121, P:450; S:6473; `backend/src/jobhunter/db/transitions.py:513`, `backend/src/jobhunter/db/migrations/versions/0006_m2_llm_profile_settings.py:354` — The registry permits only `query_proposals.running → ready|failed`; it has no transition to `purged`. The database trigger also rejects direct updates, so Task 14’s proposal-redaction test cannot pass. — Add the required purge edges, synchronize the transition matrix, and test the transition together with nulling `items`.

5. **MAJOR — Completion checks require fences to be released before the prescribed release.** P:331, P:405, P:693; S:6249, S:6275; `backend/src/jobhunter/db/guards.py:20` — `check_postconditions` requires no active fence belonging to the manifest. Both live completion and replay call it before releasing those fences. Consequently, a fenced purge fails its own completion check indefinitely. — Release fences inside the final transaction before checking the final-state postconditions, rolling everything back on failure, or explicitly separate pre-release and final-state checks.

6. **MAJOR — C31 recovery recomputes an immutable file.** P:330, P:403, P:410; S:6255, S:6277 — After `privacy.purge.after_file`, the canonical file exists but the database hash is absent. The handler recomputes content, including global identity maxima and potentially a new watermark, then attempts a write that rejects different bytes. Unrelated database activity can therefore make the required recovery permanently fail. — Adopt and validate the existing canonical file when recovering this window, then record its exact content and hash. Test recovery after unrelated identity allocation.

7. **MAJOR — The purge transaction abstraction reverses the lock order.** P:399–400; S:314; `backend/src/jobhunter/worker/operations.py:465`, `backend/src/jobhunter/scoring/targets.py:178` — `PurgeRun.chunk()` takes the operation-owner lock before the procedure acquires job locks, and before procedures such as delete-everything acquire `active_config`. The required order is configuration, jobs, then owner. — Make the chunk contract acquire configuration and the complete job set before the operation owner; explicitly leave the ranking bump until all other writes finish.

8. **MAJOR — P1 still strands ambiguous submissions and weakens foreign-result validation.** P:378–382; S:4095–4096; `backend/src/jobhunter/scoring/batch_adoption.py:299`, `tests/integration/test_batch_poll.py:438` — Deleting batch items shrinks the custom-ID set used by ambiguous adoption. The provider’s original set then partially intersects it, so adoption remains quarantined before the changed result reader runs. Separately, treating every nonexistent target as purged makes the existing `t999999_a9` foreign-result test fail. — Preserve content-free submission membership for purged items, use the original membership during adoption, and classify a missing item as purged only with positive deletion evidence.

9. **MAJOR — The shared job deletion helper omits required dependency cleanup.** P:428–429, P:470; S:6486, S:6568; `backend/src/jobhunter/dedup/representative.py:220`, `backend/src/jobhunter/db/migrations/versions/0005_m1_collection.py:589` — `representative.leave()` does not re-elect or dissolve a group, contrary to Task 13’s description. Task 15 directly uses `delete_job_graph`, whose contract covers only tombstoning steps 6–7, omitting merge-event cleanup and group re-election. Restrictive merge-event and representative foreign keys can block deletion. — Define one complete pre-deletion cleanup contract, explicitly call `reelect`/`dissolve`, and exercise merged jobs and group representatives in source-purge tests.

10. **MAJOR — Resetting defaults through ordinary settings activation can prevent delete-everything.** P:490; S:6540–6541; `backend/src/jobhunter/settings/save.py:444`, `backend/src/jobhunter/settings/save.py:299`, `backend/src/jobhunter/db/migrations/versions/0006_m2_llm_profile_settings.py:146` — `internal=True` does not bypass activation gates. Resetting a changed model policy can require schema verification; it can also create a new tuple referencing the still-active profile before the pointers are cleared. That tuple lies above the recorded deletion bound and prevents deletion of its profile. — Provide a dedicated reset path that creates only the retained default configuration, updates schedule pointers, and neither runs activation gates nor creates scoring work.

11. **MAJOR — The manifest bounds cannot represent deletion of login lockouts.** P:316–327, P:490; S:6254, S:6532; `backend/src/jobhunter/db/migrations/versions/0001_m0_baseline.py:114` — `login_lockouts` has neither an identity column, a bounded parent nor `created_at`. None of the prescribed bound types can delete its existing rows while preserving later lockouts on replay. Recording its `scope` keys would put IP addresses in manifests. — Add a content-free generation bound, such as a monotonic identity, and specify its live and replay predicates. Test a lockout created after the manifest.

12. **MAJOR — A failed delete-everything blocks its own retry route.** P:285, P:335, P:539; S:6420; `backend/src/jobhunter/db/guards.py:20` — The global fence remains after failure, and the reconciler deliberately does not retry failed operations. However, `/api/system/purges/{operation_id}/retry` matches neither exemption, so the edge rejects the only advertised recovery action. — Explicitly exempt the narrowly scoped purge-retry endpoint and test recovery through the real middleware while a global fence remains active.

13. **MAJOR — Re-authentication prevents idempotent retries with TOTP.** P:530–531, P:546; S:6512, as amended by M5-U4; `backend/src/jobhunter/auth/users.py:192`, `backend/src/jobhunter/api_idempotency.py:69` — Re-authentication consumes the TOTP step before checking the idempotency record. Retrying an accepted request with the same body therefore fails re-authentication; replacing the code changes the normal request fingerprint and produces `idempotency_key_reused`. — Define an authenticated replay path that returns an already-authorized result without consuming another TOTP step. Specify credential-independent action fingerprinting and test lost-response retries with TOTP enabled.

14. **MAJOR — An export can outlive a purge and publish deleted content.** P:407–408, P:509–510; S:6507–6508 — Golden-case deletion creates no fence. An export created after its export-ID bound is captured can snapshot the still-present case, survive the bounded export cleanup, and become ready after deletion. More generally, checking only currently active fences misses a purge that completed between an export’s snapshot and publication. — Serialize export admission with purge admission and record a durable purge generation checked at publication, including fence-free golden-case deletion. Test both overlapping schedules.

15. **MAJOR — Restore paths do not account for restic’s stored directory hierarchy.** P:357, P:671, P:714; S:6282–6287; `Dockerfile:49` — Backups contain absolute paths such as `/data/manifests/<uuid>.json`. Restoring their snapshot with target `/data/manifests` preserves that hierarchy beneath the target; it does not put the JSON directly in the manifest directory. The same issue affects the dump and CV paths. — Specify subtree restores or an explicit staging-and-copy mapping, and assert exact restored locations before invoking verification or replay.

16. **MAJOR — Restore assumes a manifest snapshot exists.** P:358, P:714–715; S:6282, S:6294 — A valid installation can have a successful backup before its first purge, hence no manifest-stream snapshot. Unconditionally restoring `latest --tag manifests` makes disaster recovery and the monthly restore test fail in that ordinary state. — Define the empty-stream case separately from repository/access failures, and test restoring a backup made before any manifest exists.

17. **MAJOR — Rotation leaves retained backups dependent on discarded keys.** P:754–756, P:821; S:5490, S:6302; `backend/src/jobhunter/crypto.py:80` — The drill verifies current ciphertext and removes the previous key, while the recovery kit retains it only during rotation. Older retained backup sets still contain CV files and TOTP ciphertext encrypted with that key. Restic’s password cannot decrypt this inner encryption. — Retain historical data keys offline for every recoverable backup generation and document how recovery selects them. Add a restore drill using a backup taken before rotation.

18. **MAJOR — A finishing run can resume a deliberately paused dead-man check.** P:217–220; S:5718; `backend/src/jobhunter/settings/save.py:335`, `backend/src/jobhunter/worker/runs.py:682` — Disabling the schedule does not cancel an existing run. Its later success ping can resume the remote check after `deadman_sync` paused it, while local `applied_paused` still says the check is paused. The tick sees no configuration difference and leaves the false alarm condition until daily reconciliation. — Serialize ping and pause decisions against current schedule state, ensuring disabled schedules remain paused. Test disabling while a scheduled run is in flight.
